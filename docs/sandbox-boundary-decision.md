## 1. 问题陈述

用户的想法清单把"真沙箱"定义为**强制隔离**，并给出三条判据：

| 判据 | 内容 | 我方现状（段二 §3.3，**未实现**） |
| --- | --- | --- |
| ① | 有**明确的白名单**定义范围 | **部分满足**：文件侧 = 只读根 + 仅挂一个 `per-run` 空工作卷；网络侧 = `--internal` 内网桥 + 仅模型网关与回调边车可达；能力侧 = `cap-drop ALL`（**这是削减，不是白名单**） |
| ② | 进程**启动时**就被系统限制 | **满足**：容器启动即进入 namespaces / cgroups / seccomp，`no-new-privileges` 阻断 setuid 提权 |
| ③ | 所有文件操作都经**内核**强制检查 | **形式满足，但"检查者"本身是攻击面**：共享宿主内核（runc），内核 LPE 即可穿透 |

**调研硬结论（有来源）**：
- gVisor 官方："用 Linux 原语做沙箱，工作量仍然只差一个系统调用就到宿主沦陷。"
- Anthropic 官方："唯一守得住的防线是环境层（出网控制 + 文件边界）"，模型层防御"永远不可能 100%"。
- → **判据③在共享内核下无法通过加固闭合；要闭合只能换边界：microVM（每 guest 独立内核）或用户态内核（gVisor）。**

**但本项目已有一个更上位的前提**（这是本裁决与"网上通常讨论"的关键差异）：

> 【事实】段二规格 **§15 #2** 原文：「**沙箱不是安全边界**：Linux 侧结论未知（前置清单 B3 ④）；即使结论是 ✅，也不改变本段的边界设计（**主机边界 + 最小挂载 + 无长寿命凭据**）。」
> 【事实】§3.3 已把边界设在**位置**（生产与工作台**分主机**）与**凭据**（容器内**不得持有任何长寿命密钥**，唯一注入物 = 我们签发的短期网关令牌，供应商密钥只在容器外的模型网关）。

**【判断】因此发现 2 不构成对现有设计的推翻**：我们**从未把安全押在容器上**，而是押在「主机边界 + 九步闸门 + 无长寿命凭据」。要补的是**把这句话变成可复现的取证**，并把"何时必须升级 microVM"写成**触发器**——而不是现在就上 microVM。

## 2. 事实基线：§3.3 已经做了什么（逐项）

| 项 | §3.3 现状 | 是否覆盖调研的 13 条红队用例 |
| --- | --- | --- |
| 位置 | 生产**与工作台分主机**（不同宿主/网络/编排域），只经一个受控执行接口 | — |

| 输出 | 路径**虚拟化** + **反向脱敏**；产物须**显式导出**（`artifact.export`，`critical`）并过内容安全检查 | 覆盖 **10 的外溢出口** |

**【判断】盘点结论：调研给出的 13 条里，§3.3 的设计**已声明覆盖约 9–10 条**。网上常见的那份"AI Agent 沙箱缺口清单"（出网白名单、密钥出容器、挂载 `noexec`、裸 `docker.sock`）**大部分是为"把容器当安全边界"的产品准备的，与我方口径不同构**——照搬会重复建设。**
**但实测同时暴露了一处反向问题**（§3.1 Probe1）：**按现状口径直接实现，工作卷不可写 ⇒ 见 G7（实现前必须修）**。

### 3.1 本轮实测证据（2026-09-15，真容器）

**方法**：一次性容器 + 一次性 `--internal` 网络；容器参数按 §3.3 口径设置（`--read-only`、工作卷 `--tmpfs`、`--cap-drop ALL`、`--security-opt no-new-privileges`、`--user 65534:65534`、`--pids-limit 128`、`--memory 256m`、`--cpus 0.5`），镜像 `python:3.12-slim`（本地已有）。**探测脚本经 stdin 传入，未落盘**；容器用 `--rm`、网络事后删除 ⇒ **残留 0（已核）**。

#### Probe 1（按 §3.3 现状口径）

| 探针 | 原始结果 | 判定 |
| --- | --- | --- |
| `resolv.conf` | `nameserver 127.0.0.11`，注释含 `ExtServers: [host(...)]` | 内嵌 DNS 存在 |
| DNS 解析 `example.com` | `gaierror: [Errno -3] Temporary failure in name resolution` | **不外泄 → G1 关闭** |
| TCP `169.254.169.254:80` | `OSError: [Errno 101] Network is unreachable` | **不可达 → G4 关闭** |
| TCP `1.1.1.1:443` / `8.8.8.8:53` / 裸 UDP DNS `1.1.1.1` | 全部 `[Errno 101] Network is unreachable` | **`--internal` 下零出网** |
| 只读根 | `mount:/ = overlay ro,…` | 生效 |
| 越界写 `/etc/probe.txt` | `OSError: [Errno 30] Read-only file system` | 生效 |
| 越界读 `/etc/shadow` | `PermissionError` | 生效（非 root） |
| 权限与 seccomp | `uid:gid=65534:65534`、`CapEff=0`、`CapBnd=0`、`NoNewPrivs=1`、`Seccomp=2` | **判据② 实测成立** |

#### Probe 1′（更正实验：A/B/C 三组对照，同镜像同加固参数）

Probe 1 把"写失败"归因于"缺 `uid/gid`"，**该归因是错的**。三组对照：

| 组 | 口径 | 工作卷实际 mode | 写入结果 |
| --- | --- | --- | --- |
| A | 执行器口径（带 `size=64m`，**无 `--workdir`**） | `0o41777` | **WROTE_OK** |
| B | 无 `size` 且 **带 `--workdir /workspace`** | `0o40755` | **PermissionError [Errno 13]** |
| C | 无 `size`、**无 `--workdir`** | `0o41777` | **WROTE_OK** |

⇒ **决定因素是 `--workdir` 指向该 tmpfs**（Docker 会把该挂载改写成 `mode=755`），**不是缺 `uid/gid`**。
⇒ **执行器不传 `--workdir`，故"当前实现即有功能性缺陷"不成立**——**原 G7 是假阳性，源于探针口径与执行器口径不一致**（诚实登记：这是本项目第 4 次"我方判断被证据推翻"）。
⇒ **残留真问题见 G7′**（已修）。

#### Probe 2（G7 修法验证）

把工作卷改为 `…,uid=65534,gid=65534,mode=700`，`/tmp` 与 `/dev/shm` 改为 `…,uid=65534,gid=65534,mode=1777`：

| 探针 | 结果 |
| --- | --- |
| 写 `/workspace`、`/tmp`、`/dev/shm` | **三处全部 SUCCEEDED**（`stat` 确认 `mode=0o700 uid=65534` / `0o1777`） |
| 挂载项 | 三处仍为 `rw,nosuid,nodev,noexec` ⇒ **加固项未被削弱** |
| 直接执行工作卷内脚本 `/workspace/runme.sh`（已 `chmod 755`） | `PermissionError: [Errno 13] Permission denied` ⇒ **`noexec` 生效** |
| 🟡 **解释器加载** `python /workspace/bye.py` | **`RAN`（输出 `INTERPRETER-RAN`）** ⇒ **`noexec` 挡不住解释器** |

#### 由此得到的一条规格论证修正（G8）

【判断】§3.3 把"工作卷 `noexec`"列为 §3.2 局限 5（同名替换）的**第二道**防线。实测表明：**`noexec` 只能阻止"直接 exec 该文件"，不能阻止"用解释器加载该文件"**（容器内必然有 python/node 等解释器，这是工具能运行的前提）。⇒ 建议在 §3.3 写明 `noexec` 的**作用边界**，并明确"**第一道仍是 §3.2 的 ④-0 可执行文件来源校验**，`noexec` 不是充分防线"，避免被读成"工作卷内不可能执行任何代码"。
✅ **已写（2026-09-15）**：规格 §3.3 **文件系统行**末段（G8 括注）与 `app/tool_execution/executor.py` 模块 docstring 均已写明该作用边界。

#### Probe 3（**G5 反假矩阵**，2026-09-15 本机真容器）

一次运行：`py -m pytest -o addopts="" tests/test_exec_sandbox_escape.py` ⇒ **14 passed**（13 条逃逸 + 1 条静态兜底）；**逐条原始输出**与完整矩阵见规格 §5「G5 实测证据」块。摘要：

| F | 装配期白名单校验置空 | **G2 用例**（`DID NOT RAISE`） |

【判断·**判据修正**（本轮实测得出）】**`--cap-drop ALL` 对非 root 用户的效力主要在 bounding set**：置空后 `CapBnd` 恢复为 `00000000a80425fb`，而 `CapEff` 仍为 `0000000000000000`（Docker **不会**给非 root 用户补 effective 能力）⇒ **越界读 / 提权的第二道防线实际来自「非 root 身份」，不是 `--cap-drop`**。故这两类用例的"必须红"应以 **改回 root（`--user 0:0`）** 构造；"加回 cap"式改法**不构成有效放宽**（实测仍绿）。结论已同步进规格 §5 行 37 / 38 / 44 / 46。

【判断·**反假方式的边界**】用例 **41（云元数据）** 的反假在本机与 CI（`ubuntu-latest`）**均不可构造**——两边都没有云元数据端点，放开网络也没有目标可连 ⇒ 该条只能"断言不可达"，**不能证明"放开网络就会红"**；要真正验证需在**云主机**上跑一次。用例 **45（持久化外溢）/ 48（Windows 穿透通道）** 的反假需改工作卷落点／挂宿主盘，本轮**未构造**（断言本身已实跑通过）。

#### 本轮实测的边界（不得超出）

1. **宿主相关**：本次在**本机 Docker（Windows + Docker Desktop / containerd snapshotter）** 测得。`--internal` 的出网与解析行为**必须在真实生产宿主（Linux）与 CI 中复测**——**本次结论不得直接外推到生产拓扑**。
2. **未覆盖**：fork 炸弹实测、tmpfs 容量耗尽实测、`--pids-limit` 生效实测、孤儿容器回收实测、产物导出通道实测；§3.2 九步闸门相关用例属另一批。
3. **未做反假**：本轮是"探针测现状 + 修法验证"，**尚未做"故意放宽策略必须变红"的反假**（属 G5 落地内容）。

## 4. 三个选项

### 选项 A：维持"强化容器 + 容器不是安全边界"（= 现状口径 + 修 G7 + 补 G2/G5/G8；G1/G3/G4 已实测关闭）

- **内容**：不改容器运行时；把 §15 #2 的声明**写硬**（明示"容器是**风险削减措施**，不是安全边界；边界在主机 + 闸门 + 凭据"）；**修 G7**、补 **G2/G5/G8**（G1/G3/G4 已实测关闭）；把逃逸回归进 CI。
- **代价**：低（不换技术栈、不改容器实现）。
- **残余风险**：宿主内核 LPE / 容器运行时漏洞 ⇒ 可能逃逸到**执行主机**。**但**：执行主机与工作台**分主机**、容器内**无长寿命凭据**、出口**无外网**（`--internal`）、产物**须显式导出并过内容安全检查** ⇒ 逃逸后的可得性被大幅削弱。
- **适用**：**当前阶段（单租户/内网私有化、执行主机专属）**。

### 选项 B：升级为 microVM（独立内核）

- **内容**：Linux 服务器侧 → **Kata Containers**（生态最成熟，VMM 可选 Cloud Hypervisor / Firecracker / QEMU）/ **腾讯云 Cube Sandbox**（**Apache-2.0**，RustVMM + KVM，**原生兼容 E2B SDK**，宣称冷启动 <60ms 且单实例 <5MB，已用于腾讯云生产）/ **gVisor**（无需 KVM，嵌套虚拟化受限时的选择）。桌面侧 → **Docker Sandboxes（`sbx`）**（microVM，Windows 走 Windows Hypervisor Platform；CLI 免费含商用）。
- **收益**：**真正闭合判据③**（每 guest 独立内核）。
- **代价**：中-高。Kata/Cube 需改执行主机运维与镜像形态；gVisor 有兼容性矩阵（不支持 `io_uring` 默认禁、`userfaultfd`、eBPF、容器内 KVM、块设备挂载）；microVM 有启动开销。
- **【判断】**注意：**委托方的 12 条清单不因换 microVM 而变少**——Red Hat 实验结论是"**VM 挡内核漏洞但不拦外泄，应用层 egress 策略拦外泄但不挡内核漏洞，必须叠加**"。换边界**不能替代** G1（DNS/出网）与九步闸门。

### 选项 C：A + 明文化的"microVM 触发器"（= A 为现状，B 在条件命中时执行）

- **内容**：现在执行 A（含修 G7 与补 G2/G5/G8）；同时把**何时必须升级 B** 写成触发条件，登记进规格 §8（未闭环项）或变更记录。
- **建议的触发器（任一命中即启动 B 的专项评审）**：
  1. **执行容器与生产数据落在同一宿主**（放弃"分主机"）；
  2. **多租户共享同一执行主机**（租户间不再是"我们 vs 我们"的关系）；
  3. **对外提供"执行即服务"**（托管他人代码）；
  4. **出现针对我们所选运行时的真实逃逸事件或高危 CVE 命中**；
  5. **合规/客户明确要求"独立内核"**（例如等保/信创评审提出）。
- **代价**：低（现在）+ 未来按需。
- **风险**：若触发器写得太宽，会退化成"永远不做 B"；若太窄，会漏掉真实威胁。→ 建议**同时**保留 E1（eBPF 运行时强制）作为"不换边界但增强止损"的中间档，避免"只有 A 和 B 两个选项"的二元化。

## 5. 建议

**【判断】建议选 选项 C。**

理由（逐条给依据）：
1. **与上位口径自洽**：§15 #2 已声明"沙箱不是安全边界"，边界在主机 + 闸门 + 凭据；A 不改变该口径，只把声明变成取证。选 B 会把边界**重新搬回容器层**，反而与既有设计哲学冲突（且 B 也不能替代闸门与出网控制）。
2. **成本-收益匹配当前阶段**：当前是**单租户、内网私有化、执行主机专属**场景；按发现 2 的事故共性，真正致命的是"**闸门写在 prompt 里**"与"**审计以 Agent 自述为准**"——这两点我们已在九步闸门与 append-only 审计里处理，属**已投入的正确方向**。
3. **不阻塞在飞工作**：A 不改容器实现，段二 §3.3 可按现有口径往下走；G1–G5 是**增量补强**，不影响既有回归套件与交付节奏。
4. **B 的收益是"闭合判据③"，而判据③并不是我们的边界**：调研自己给出的行业教训是"**VM 挡内核漏洞但不拦外泄**"——所以 B 的必要性取决于**威胁模型**（谁在共享这台执行主机、数据有多敏感），而这两者由 §5 的触发器刻画比"现在就上"更准确。
5. **保留中间档**：E1（eBPF 运行时强制）能在**不换边界**的前提下把"漏了能立刻止住"补上，避免二元化。
