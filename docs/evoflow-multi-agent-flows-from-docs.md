## 0. 一句话结论

它的协作模型可以概括为：**「岗位合同 + 计划落库授权 + 两道人闸 + 双通道派活」**。
真正值得我们拿走的不是"多 Agent 并行"这个说法，而是下面四个**流程机制**（详见 §5）。

## 3. 三条主流程逐步拆解

### 3.1 Plan 模式（先定稿、再授权执行）

```
① 发需求
   └→ 助手先「摸底澄清」
② 调用 plan 工具 → 计划**落库到任务表**
   └→ 消息区出现 plan 摘要
③ 输入框上方出现「确认条」
   kicker「计划已定稿」／状态「待授权开始执行」／N 步骤
④ 点「查看计划」→ 弹窗（目标 / 执行步骤 / 整体验收）
⑤ 改计划：**在下方输入框说修改意见**（⚠️ 没有独立的「修改计划」按钮）
⑥ 点「开始执行」→ 自动打开**右侧工作流 DAG**
⑦ 可选：「另存为应用」「不再提示」
```

**两个关键设计**（原文口径）：
- **子任务在 `plan` 成功时就已同步创建，但"授权前故意隐藏"** —— 未定稿授权时侧栏**不显示**子任务。这是"先定稿再暴露"的取舍。
- **授权后不自动跳转任务中心**（留在对话里看 DAG）。

**项目团队版**固定 7 阶段：`澄清 → 调研 → plan 落库 → 等待授权 → supervisor(start_execution) → 监工（monitor_execution_step / steer_subtask / retry_subtask）→ 对照 validation 总验收`。

### 3.2 Goal 模式（自驱多轮，到边界才停）

与 Plan 的**唯一本质区别**：**不用你每步确认，自驱多轮直到边界**。

| 维度 | 文档口径 |
| --- | --- |
| 入口 | 仅聊天里的「目标」药丸 |
| 启动 | 对话触发 `propose_goal` → 返回**确认条**（填入并开始 / 仅填入 / 取消）；**「主智能体不会绕过确认条自行启动」** |
| 状态机 | `idle → running → waiting → paused → error` |
| 等待 | 主控需补充信息 → 自动转 `waiting`，**最长等 7 天** |
| 恢复 | 暂停**保留上下文**；恢复「从上一轮的安全断点接续」 |
| 终止 | 终止 → `idle`，**产物全留**；可"基于刚才产物继续" |
| 边界 | `max_steps`（默认 8）与 `auto_stop_minutes` **先到先停** |
| 并发 | 单会话**同时只允许 1 个活跃目标** |

### 3.3 任务中心闭环（无人值守流水线）

```
创建 pending
  → 队列 tick
  → 规划 planning
  → 已规划 planned
  → 授权
  → 派发 executing
  → 完成 completed
```

**状态全表**：待开始 / 规划中 / 已规划 / 执行中 / **待闭环** / **待确认** / 已暂停 / 已完成 / 失败 / 已取消。

**🔴 最值得学的一条：三态严格区分（原文口径）**

| 状态 | 含义 |
| --- | --- |
| **待审批** | **放行、叫醒下游** |
| **待闭环** | **本岗已交，整单未关** |
| **待确认** | **人认不认结果** |

**决策区**：待确认 → 确认完成 / 打回重做 / 标记失败 / 取消 / 删除；失败 → 再跑一次 / 查看工作流 / 删除。**失败默认自动重试 3 次。**

## 4. 「智能体员工」值班机制

| 机制 | 文档口径 |
| --- | --- |
| **自动上班** | `#/proactive` 值班台总开关 + 「上班频率」（心跳 RRULE：10/30 分钟、1/2/3 小时、每天 9:00）+「上班时间」；**窗外一般不自动心跳，但「现在开始工作」不受限制** |
| **触发入口（7 个）** | 自动上班 / 现在开始工作 / 派发任务 / 小 V 委派 / 同事跨岗叫醒 / 正式交工过门 / 下游回执 / 事件触发 |
| **汇报** | 每轮「本轮小结（wrap_up）」；工作日志 `#/proactive/:code`；产出写 `docs/roles/<agent_code>/<YYYYMMDD-HH>/` |
| **催办** | 设「系统前台」岗偏催办全局待办；总监岗自动上班扫下级阻塞并提醒未闭环项 |
| **两道闸（勿混）** | ① **交接审批「同意派发」** = 放行叫醒下游；② **「确认完成 / 打回重做」** = 验收 |
| **审批策略 × 风险** | 全自动 / 平衡 / 谨慎 × 任务风险 → 决定是否要人工点「同意派发」 |
| **KPI** | **文档未说明**。只有「健康」Tab：今日成本、卡住执行（>45 分钟）、疑似空转、预算告警、卡片「摸鱼中」 |

## 5. 对我们的价值：值得拿走的 8 条（按优先级）

> 全部为**流程机制**，不涉及代码。

| # | 机制 | 为什么对我们有用 |
| --- | --- | --- |
| 1 | **两道闸分离**：`同意派发`（放行下游）≠ `确认完成`（验收） | 我们目前把"审批"当成一件事。拆成两道后，「待闭环」态才有意义 —— 本岗交活 ≠ 整单完成 |
| 2 | **「待闭环」态** | 解决"干完了但没人验收就消失了"。我们的运行只有 completed/failed，缺"已交未验"这一档 |
| 3 | **计划落库 + 授权前隐藏子任务 + 授权后不跳页** | 把"先定稿再暴露"做成产品行为，而不是靠提示词自律；且不打断用户当前上下文 |
| 4 | **改计划 = 在输入框说话**（没有独立"修改计划"按钮） | 少一个控件、多一条自然语言路径 —— 与我们"以人为本、可直接说话"的方向一致 |
| 5 | **Goal 的「不绕过确认条自行启动」+ 单会话只允许 1 个活跃目标** | 自治能力再强也保留一个显式确认点，且限制并发避免失控 |
| 6 | **交工只对直属下级、同级只能"叫醒"的双通道** | 组织层级与协作效率的折中；避免"谁都能往任何人头上压活" |
| 7 | **失败默认自动重试 3 次** + 健康 Tab 的"卡住执行（>45 分钟）/ 疑似空转" | 可运维性：把"看起来在跑其实卡住"变成可见指标 |
| 8 | **跑通后「另存为应用」** | 把一次性成功固化成可复用资产（与我们 P5a 的"从成功任务固化"同向） |
