## ADR-0001 后端技术栈：保留既有 Python 服务，不重写为 NestJS

**状态**：**已裁决（2026-09-19，用户确认）：采纳** —— 保留 Python 后端，不重写 NestJS。

**背景（实测）**
- 仓库既有后端为 Python 服务：`app/` + Celery worker + PostgreSQL/pgvector + Redis；**44 个迁移**、**2600+ 自动化用例**、已完成商业化生命周期、记忆层、技能层、知识治理、工作台闭环 S1–S6、清场扩围等。
- 《项目核心规范》写"后端：NestJS"；《开发设计规则》§6.1 写"**按团队现有技术栈**，推荐 Node.js/NestJS 或 Java/Spring Boot"——两份文件本身口径不同。

**决策提议**：**保留 Python 后端**；不引入 NestJS。前端与后端以既有 HTTP 契约（`docs/api-contract.md`）交互，新工作台能力在后端**新增模块**而非重写。

**理由**
1. 重写 = 把已验证的 2600+ 用例、44 个迁移与所有安全边界（多租户、权限、审计、保留策略）推倒重来，与《开发设计规则》§2.6"测试契约锁架构"直接冲突；
2. 规范要求的 PostgreSQL + pgvector + Redis，既有实现**完全一致**（无需更换数据层）；
3. 保留后端不影响前端按规范换栈（见 ADR-0003）——两条决策互不绑定。

**替代方案与代价**
- 方案 B（重写 NestJS）：需重做全部数据模型与安全边界，工期与风险极大；且 TypeScript 侧没有现成的 44 迁移/2600 用例资产。**不推荐**。

**知识库既有结论（强化本提议，原文核对）**：生态内的《总体思路复审-2026-09-03》明确把「一开始把 Celery 全部替换为 Temporal」「把 MySQL 改为 PostgreSQL」等列为**不应成为第一期前提**的技术改造；并约定「工作台**不应复制**既有能力，也不应让桌面端/手机端直接访问数据库，客户端只调用版本化工作台 API」。⇒ 与"保留 Python 后端 + 只做增量模块"完全一致。

**影响面**：技术栈文档、AI 上下文文件（"AI 每次读取"那份）需写明"后端 Python，前端按规范"。

**签字**：`[x] 采纳（保留 Python）` —— **已裁决 2026-09-19**（未选项「改为 NestJS 重写」已记录为否决）—— 签字人：用户 日期：2026-09-19

## ADR-0002 多租户隔离：**已裁决为 Schema 级**（推翻本 ADR 原提议）

**状态**：**已裁决（2026-09-19，用户确认）：要求 Schema 级隔离** —— 本 ADR 的"保留行级"提议**被否决**；
按《开发设计规则》"地基不随手翻"，Schema 级改造成立**专项**：需另出**《Schema 级多租户改造专项方案》**（含分期、迁移策略、回退方案）并经评审后才可动工。**在专项方案签字前，任何实现不得开工。**

**已定的方向性要求（本 ADR 锁定）**
1. 数据隔离级别 = **Schema 级**（每个租户一套 schema），不再是行级 `tenant_id` 过滤为主；
2. 租户上下文仍**由后端强制注入**（前端不可篡改），且注入点必须与 schema 路由**同一处解析**（避免"注入了 A 租户、连到 B schema"的错配）；
3. 高敏感租户独立数据库 = 该模型的自然延伸（后续 ADR）。

**必须由专项方案回答的问题（缺一不可，建议逐条签字）**
1. **迁移策略**：现有 **44 个迁移 / 55 张租户级表**如何从 `public` 行级迁到 per-tenant schema（一次性 vs 双写期；历史数据搬运与校验方式）；
2. **新建租户**：schema 创建时机（注册即建 vs 首次登录懒建）、命名规则、失败补偿；
3. **连接与事务路由**：连接池如何按租户选 schema（`search_path` vs 独立连接）、事务内跨 schema 是否一律禁止；
4. **跨租户运维**：备份 / 恢复 / 统计 / 定时任务（worker 需遍历全部租户）如何改造；
5. **平台级表**的归属（`workbench_tenants`、审计、保留策略、生命周期作业等是否留在 shared schema）；
6. **回退方案**：上线后如何退回行级（或前滚修复），以及演练方式（对齐既有"迁移 + 回退演练"口径）；
7. **性能影响**：schema 数增长后的连接/迁移耗时与监控口径（含"权限校验 ≤5ms"是否受影响）。

**代价与风险（如实登记）**
- 这是**地基级变更**：涉及全部查询路径与全部迁移；现有 2600+ 用例中凡以行级假设写成断言的都需重审；
- 与 ADR-0001（保留 Python）不冲突，但与"第一期只验证一个闭环"（ADR-0005）**存在资源竞争** —— 需在专项方案里排先后。

**签字**：`[ ] 采纳（行级加固）`（**已被否决 2026-09-19**） ｜ `[x] 要求 Schema 级（另开迁移专项）` —— **已裁决 2026-09-19** —— 签字人：用户 日期：2026-09-19

### 原提议（存档 · 2026-09-19 被否决，保留以便追溯）

**背景（实测）**
- 现状：**行级隔离**——55 张租户级表全部带 `tenant_id`，跨表用**复合外键**（如 `(tenant_id, conversation_id)`）在数据库层拒绝跨租户写入；租户上下文由服务端从认证上下文注入，客户端传 `tenant_id` 不改变数据范围（已写入契约）。
- PRD 验收标准原文是："租户间数据完全隔离，**无交叉访问可能**"——该性质由现有机制可证（并已有跨租户用例）。

**决策提议**：**保留行级隔离并加固**（补齐跨租户用例覆盖面 + 逐行审核清单），**不落地 Schema 级**；"高敏感租户独立数据库"用**独立实例部署**满足（部署形态，不改数据模型）。

**理由**
1. 规范的可验证目标是"无交叉访问"，行级 + 复合外键 + 服务端注入已满足，且能直接写测试证明；
2. Schema 级代价极高：55 表 × N 租户的迁移与版本管理、连接/事务路由、跨租户运维脚本重写、备份恢复与监控复杂度成倍上升——当前为单人主导开发，维护风险过大；
3. 现存 44 个迁移与全部查询均以行级为前提，切换等于重做数据层（与 ADR-0001 的重写风险同级）。

**替代方案与代价**
- 方案 B（Schema 级）：需专项迁移 ADR + 分阶段执行（先新表、后历史表、再切读写路径），并按《开发设计规则》"地基不随手翻"走评审。

**影响面（原提议，已作废）**：~~PRD 中 MT-01 的实现口径改写为"行级隔离 + 复合外键 + 服务端注入"~~ ⇒ **作废**：MT-01 按 Schema 级实现（见上方裁决）。

**签字（原提议 · 存档）**：~~`[ ] 采纳（行级加固）` / `[ ] 要求 Schema 级`~~ ⇒ 已由上方裁决取代。

## ADR-0003 前端栈与设计令牌：采纳规范（AntD 5 + ProComponents + 规范令牌值），存量页面渐进替换

**状态**：**已裁决（2026-09-19，用户确认）** —— 本工作台**采纳 AntD 5 + ProComponents + 规范令牌值**；与 GEO（React 19 + Vite + Tailwind，50+ 路由）**各自独立、仅共享令牌值**（依据：`项目边界审计-2026-09-05` 确认「GEO 仓库与公司工作台仓库相互独立，未发现串库」）；存量页面按"应用壳 → 组件库 → 逐模块"渐进替换。

**背景（实测）**
- 现状：`admin-web` / `companion-pwa` / `desktop` 三个前端**均未引入** `antd` / `@ant-design/pro-components` / `zustand` / `@tanstack/react-query`，是手写组件 + 自有令牌（`admin-web/src/styles/tokens.css`，标注"UI v2 规格逐字落地"，含明暗双主题与对比度校验脚本）。
- 规范值 vs 现状值（逐值比对）：主色 `#1677FF` vs `#4f46e5`；圆角 卡片 8/按钮 6/标签 4 vs 10/14/8；字号 12/14/16/20/24 vs 11/12/14/15/26；间距"仅 8 的倍数" vs 现值含 4/12/20；阴影"0 1px 2px rgba(16,24,40,.04)" vs 卡片**不用阴影**；`#F5F7FA` / `#E5E7EB` vs `#f7f7f9` / `#e7e7ec`；**一致项**：辅助文字 `#6B7280`、侧栏 240px、顶栏 56px。

**决策提议**：**采纳规范** —— 新工作台 UI 使用 **React + Ant Design 5 + ProComponents + Zustand + TanStack Query**，颜色/间距/圆角一律引用规范令牌；**存量页面不一次性重写**，按"应用壳 → 组件库 → 逐模块"渐进替换（符合纠偏话术"输出 diff，不要重写整个项目"）。

**理由**
1. 规范是既定目标，且 AntD 默认主色即 `#1677FF`，与其主题 token 体系天然对齐（省掉自造组件库）；
2. PRD 明确要消除"界面粗糙、交互复杂、程序员化"——统一组件库是达成该目标的最短路径；
3. 渐进替换避免一次性重写导致 `admin-web` 现有 354 条前端用例大面积失效。

**实施注意（技术事实，非风格偏好）**
- 主色 `#1677FF` 作**组件底色**可用；但**正文/链接**若用同色，与白底对比约 3.4:1，**不满足 4.5:1**。建议正文/链接取 AntD 深一档（blue-7 `#0958d9`），并复用仓库既有 `check:contrast` 脚本回归；
- 间距"仅 8 的倍数"与 AntD 默认 `padding 12/20` 冲突 ⇒ 用 AntD 主题 token 覆盖为 8/16/24/32，否则每次都要手动改；
- 深色模式：规范未给深色值 ⇒ 暂按 AntD 算法主题生成，**登记为待补规范**。

**替代方案与代价**
- 方案 B（保留手写组件库 + 只对齐令牌值）：改动小、存量用例零失效，但**违反"使用 Ant Design 组件，禁止用 div 模拟按钮/表格/下拉"**，且需自己维护表格/表单/抽屉等重型组件。**不推荐**。

**生态一致性提示（已裁决处置）**：GEO 前端为 React 19 + Vite + Tailwind（原文核对 `wiki/entities/智曜GEO.md`）；经你 2026-09-19 裁决：**两者各自独立、仅共享令牌值**，本 ADR 不再考虑与 GEO 壳层收敛。

**签字**：`[x] 采纳（AntD 5 + 规范令牌，渐进替换）` —— **已裁决 2026-09-19**；`[x] 与 GEO 各自独立、仅共享令牌值` —— **已裁决 2026-09-19**（未选项：与 GEO 统一为 Tailwind 路线 / 统一为 AntD 路线，均已记录为否决）。

## ADR-0004 数据分级与组织维度：ACL 采用规范 4 级（新建文档级标签），保留既有 5 级用于模型路由，暂不引入"部门"实体

**状态**：提议（待签字）

**背景（实测）**
- 文档表 `workbench_knowledge_documents` **无任何 ACL/敏感级别字段**；访问控制现状 = 库级绑定（角色/员工 ↔ 知识库）+ 治理状态机 + 负责人闸门。
- 既有 `DataClassification` 为 **5 级**（public/internal/confidential/sensitive/restricted），**用于模型路由**（按数据级别选模型），不是文档可见性。
- 平台**无部门实体**（`app/crm/models.py` 注："平台无部门维度数据"），只有 `department_lead` 角色名。

**决策提议**
1. **文档 ACL 新建 4 级**：`public` / `internal` / `confidential` / `restricted`（= 公开 / 内部 / 机密 / 绝密），落在知识治理层，作为**可见性**的唯一判据；
2. **模型路由 5 级保持不变**，两套之间建立**显式映射**（详见 `knowledge-acl.md` §4），且"模型路由级别只升不降"（绝密不得路由到低保障模型）；
3. **暂不引入部门实体**：ABAC 先只用 `tenant_id` + `project_id` + `ACL 级别`；"部门管理员"由 `department_lead` 角色 + 库级绑定表达；
4. 若后续要真引入部门 ⇒ 另开 ADR，且必须与身份源对接（LDAP/钉钉/飞书组织同步）同批，否则部门数据来源不清、权限会失真。

**理由**：4 级是 PRD 与规范的明文要求（KB-01）；5 级是既有模型路由资产，改它会牵动模型选择与执行链路；部门维度缺数据来源，硬做只会造出"空部门"。

**替代方案与代价**
- 方案 B（沿用 5 级做 ACL）：违反规范且语义混淆（`sensitive` 与 `restricted` 的可见性差异无法向用户解释）。**不推荐**。
- 方案 C（立刻引入部门）：需先做身份源组织同步（属 P1 准备清单第 2 项），否则是假权限。

**⚠️ 追加裁决项（知识库既有事实，2026-09-19 复核原文）**：生态内的**平台侧岗位体系已在使用"组织"维度**——`媒体资源目录权限一致性修复-2026-09-04` 明确记载：岗位须**绑定同一组织、范围=组织**，且「跨组织岗位」「未绑定组织范围的岗位」**一律明确拒绝**（该修复正是补上这条漏洞）。
⇒ 因此"部门/组织"不是"要不要引入"的纯新议题，而是**是否与既有平台岗位体系对齐**：若本工作台的岗位/权限要与该体系对接（或由同一套账号体系承载），组织维度**是既有事实**，应改为采纳；若本工作台自成一套（独立租户内角色），则维持"暂不引入"。
**这条必须你明确选一个**（我不擅自翻转）：

**签字（分两部分，请留意只签了前半）**：
- 组织维度：`[x] 采纳 A 案 —— 暂不引入组织/部门实体 + 保留扩展位` —— **已裁决 2026-09-19**（未选项：立刻对齐平台组织体系 / 彻底不做预留，均已记录为否决；否决"立刻对齐"的依据 = 两仓库已审计相互独立 + 平台无部门数据来源）。
- 文档分级：`[x] 采纳（ACL 4 级 + 与路由 5 级的映射表）` —— **已裁决 2026-09-19**（未选项「改用 5 级做 ACL」已记录为否决）—— 签字人：用户 日期：2026-09-19

## ADR-0005 第一期边界与试点范围：沿用知识库已冻结结论，不新增范围

**状态**：**已裁决（2026-09-19，用户确认）：扩大第一期范围** —— 既有的"一个闭环 + 自媒体运营/CEO 看板试点"作为**基线保留**，另按用户选择**并入若干 P0/P1 项**（清单见下方"第一期范围（已裁决）"，待用户勾选后落定）。

**背景（实测）**：知识库《智曜GEO与数字员工工作台总体思路复审-2026-09-03》已冻结第一期边界与试点：
- **第一期只验证一个完整闭环**：`岗位入口 → 数字员工理解需求 → 生成任务计划 → 权限/预算检查 → 执行 → 证据/结果 → 人工审批 → 任务完成或回滚`；
- **首批试点 = 自媒体运营 + CEO 看板**（内部生产轨）；摄影剪辑、Vibe Coding 放后续批次；
- **不阻塞第一期**：应用商城、第三方 Skill、全量平台采集、本地视频大模型、完整客户 SaaS；
- 工作台**承担统一入口/岗位权限/任务中心/审批/通知/模型治理**，既有业务系统作为"业务能力包"经**适配器**接入；客户端只调用版本化工作台 API，**不直连数据库**。

**决策提议**：**采纳上述边界**，本项目的第 1 轮起工作（应用壳 → 组件库 → 逐模块）**只服务于该闭环**；不在第一期范围内做 PRD 里的 P1/P2（Agent Teams、共享、进化、混合劳动力分析、通用智能体悬浮入口等）。

**理由**：这是既有复审的明确结论，且与"每轮只做一件事""不顺手加功能"的纪律一致；避免第一期被 14 个入口拉散。

**与 PRD 的关系（如实说明）**：PRD 的验收标准是"所有 P0 需求通过测试，P1 完成 ≥ 80%"——**范围大于**本 ADR 的第一期闭环。两者不冲突但**阶段不同**：本 ADR 管"第一期做什么"，PRD 管"整期验收"。若你要把某些 P0（如通用智能体 GA-01/02、岗位模板 DE-01）**提前到第一期**，请在此处写明。
