### 选项

| 选项 | 做什么 | 要动多少 | 后果 |
| --- | --- | --- | --- |
| **A. 保留 AntD（workbench-web）作底座** | 把 admin-web 的功能迁进来，3,430 行 CSS **大部分被 AntD 替代**；`tokens.css` 与两个守卫脚本**单独摘出保留** | 改造 **admin-web 的 148 个文件** | ✅ AntD 的成熟组件（表格/表单/抽屉/日期/树）全部留住<br>⚠️ 视觉风格要重新调（AntD 默认审美与你现在的不同） |
| **B. 保留手写 CSS（admin-web）作底座** | 把 workbench-web 的功能迁进来，**63 处 AntD 用法重写成手写组件** | 重写 **workbench-web 的 125 个文件** | ✅ 视觉风格与现有设计纪律完全保留<br>❌ **要自己重写表格/表单/抽屉/日期选择器**——这是最大成本 |
| **C. 混合**：手写 CSS 做壳 + AntD 做业务组件 | 壳层（侧栏/布局/三栏）用手写 CSS；业务组件用 AntD | 中等 | ✅ 壳的风格可控 + 组件的开发速度快<br>⚠️ 两套样式体系并存，需要明确的边界规则 |

### 我的推荐：**C（混合），退化到 A**

**理由**：
1. **AntD 那 63 处用法是资产不是负担**——表格、表单、抽屉、日期选择器**重写成本极高**（admin-web 现在是自己写的，那些 `ui.css` 919 行就是在重造这些轮子）
2. **admin-web 最值钱的 CSS 是 `tokens.css`（127 行）**——设计令牌与 UI 框架无关**可以摘出来用**，**但取值须按 ADR-0003 重赋**（见下方补正）
3. **`legacy.css`（1,100 行）从命名看就是历史债**——迁移时**可以直接丢**
4. **两个守卫脚本（`check:contrast` / `check:ui-copy`）与 UI 框架无关**——必须保留
5. **C 的理由**：你的设计纪律（令牌 + 守卫）体现在**壳层**，而壳层手写 CSS 更可控；业务组件交给 AntD 更快
