## 2. ⭐ 本轮最重要的发现：**一个闸门守着 9 个端点**

### 2.1 闸门原文（`app/main.py:1362`，实测）

```python
def _require_workforce_directory_admin(context: UserContext) -> None:
    if context.role != "super_admin":
        raise HTTPException(status_code=403, detail="只有超级管理员可以管理岗位与数字员工目录")
```

⇒ **规格断点 2 被真代码证实**：目录管理确实仅 `super_admin`，403 文案就是上面那句。

### 2.2 但它被**共用**（实测：**9** 个调用点（`grep -c` 会把函数定义那行也算进去 ⇒ 显示 10），逐行定位了 8 处）

| 调用点 | 端点 | 性质 |
| --- | --- | --- |
| `:1497` | `GET /api/v1/workforce/roles` | **读** |
| `:1511` | `POST /api/v1/workforce/roles` | **管理（改岗位）** |
| `:1526` | `PATCH /api/v1/workforce/roles/{role_key}` | **管理（改岗位）** |
| `:1549` | `GET /api/v1/workforce/agents` | **读** |
| `:1574` | `POST /api/v1/workforce/agents` | **管理（建员工）** |
| `:1593` | `PATCH /api/v1/workforce/agents/{agent_key}` | **管理（改/停用员工）** |
| `:1611` | `GET /api/v1/workforce/candidates` | **读** |
| `:3065` | `GET /api/v1/workforce/agents/{agent_key}/config` | **敏感读**（提示词/模型/日预算/审批档） |

> 另 2 处调用点**未逐行定位**（见 §9 未验证）。

### 2.3 ⇒ **C3 的做法不能是"放宽这一个函数"**

只把它从"仅超管"改成"四档"，会**同时放开**：

- ✅ 员工**要**的：读目录
- ❌ 员工**不该**有的：**建/改岗位**、**改/停用别人的员工**
- ❌ 更敏感的：读**任意**员工的 `config`

而 B2 给 `use` 档定的语义明确写着「**能派活；不能改配置、不能停用**」—— **直接冲突**。

### 2.4 ⇒ B2 必须**拆闸门**（至少三档）

| 新闸门 | 覆盖 | 建议口径 |
| --- | --- | --- |
| **① 读目录** | `roster` / `agents` 列表 | 放宽到四档 **+ 按 `owner_user_id` / `visibility` / shares 过滤** |
| **② 员工侧创建**（新语义） | 新的创建路径 | 四档 **+ 只能建自己的**（owner = 自己）**+ 只能从模板** |
| **③ 目录管理** | `roles` 增改、`agents` 改/停用、**config 读写** | **保持仅超管** |

**⚠️ 这条按宪法属「地基级」（权限模型）变更**，评审时**应单列**，不该混在"补接口"里评估。

## 4. 数据模型：**定义在 B1 §3.3，不在 B2**

B2 §3 开头即写「**引用 B1 规格 §3.3，本文不重写**」。字段级 DDL 在
[`2026-09-22-desktop-execution-and-client-merge-design.md`](../superpowers/specs/2026-09-22-desktop-execution-and-client-merge-design.md) **§3.3（约 166 行起）**：

### ① 改 `workbench_digital_employees`（能力包层）

```sql
ALTER TABLE workbench_digital_employees
  ADD COLUMN IF NOT EXISTS visibility TEXT NOT NULL DEFAULT 'private'
    CHECK (visibility IN ('private', 'shared'));
ALTER TABLE workbench_digital_employees
  ADD COLUMN IF NOT EXISTS owner_user_id TEXT;
UPDATE workbench_digital_employees SET owner_user_id = created_by WHERE owner_user_id IS NULL;
ALTER TABLE workbench_digital_employees ALTER COLUMN owner_user_id SET NOT NULL;
CREATE INDEX IF NOT EXISTS idx_wde_owner ON workbench_digital_employees (tenant_id, owner_user_id);
```

> `role_key`（复合外键指向 `workbench_job_roles`）**保留不动** —— 它是"岗位"，与 owner **正交**。

### ② 新增 `workbench_employee_shares`（共享层）

```sql
CREATE TABLE IF NOT EXISTS workbench_employee_shares (
  tenant_id       TEXT NOT NULL,
  agent_key       TEXT NOT NULL,
  grantee_user_id TEXT NOT NULL,
  permission      TEXT NOT NULL CHECK (permission IN ('read', 'use')),
  granted_by      TEXT NOT NULL,
  granted_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, agent_key, grantee_user_id),
  FOREIGN KEY (tenant_id, agent_key)
    REFERENCES workbench_digital_employees (tenant_id, agent_key)
);
```

**两档语义**：`read` = 能看配置、看它干过的活，**不能派活**；`use` = 能派活，**不能改配置、不能停用**。

### ③ 该表现有列（实测，用于确认"不撞名"）

- 迁移 `022`：`tenant_id` / `agent_key` / `name` / `description` / `role_key` / `status` / `created_by` / `created_at` / `updated_at`
- 迁移 `023`：`system_prompt` / `model_key` / `temperature` / `tool_allowlist` / `memory_policy` / **`autonomy_level`** / **`risk_threshold`**

⇒ B2 要加的 `visibility` / `owner_user_id` **不与任何现有列撞名**；`soul_md` **尚不存在**（全 `migrations/` 零命中，与 §5 V4 一致）。

> **⚠️ 顺带**：`risk_threshold`（`low`/`medium`/`high`，`023:61`）B2 规格**未提及**，但它就在表上 —— 创建向导若也要设风险阈值，**别另造名字**。

## 5. 迁移：要改 **3 处**，且有一处**会静默出错**

### 5.1 该表**在租户模板链里**（实测）

`workbench_digital_employees` 在 `migrations/tenant_template/0001_tenant_baseline.sql` 里出现 **12 次**，
并在 `migrations/tenant_template/classification.json` 第 28 行登记。

⇒ **加列/加表必须同时改三处**，否则**新租户的 schema 会缺列**：

| # | 文件 | 改什么 |
| --- | --- | --- |
| 1 | **新增** `migrations/045_*.sql` | 面向当前行级库的 `ALTER` + `CREATE TABLE`（实测当前最大编号是 **044**） |
| 2 | `migrations/tenant_template/0001_tenant_baseline.sql` | **同步加**（否则与迁移漂移） |
| 3 | `migrations/tenant_template/classification.json` | **新增表** `workbench_employee_shares` 必须登记 |

改完**必须跑** `scripts/tenant_schema.py` 的 `verify`（S0 期就是靠它抓出"模板漏自增序列"的）。

### 5.2 🔴 一处**会静默出错**的地方（实测）

规格 §9.2 R5 只说「`created_by` 空值的存量行…回填前须先查」。但实测：

```
migrations/022_workforce_directory.sql:15    created_by TEXT NOT NULL,
```

**`created_by` 是 `NOT NULL`** ⇒ 那句 `SET NOT NULL` **永远不会因 NULL 而失败**。

**但**：若存量行 `created_by` 是**空字符串**，回填后 `owner_user_id` 就是**空串**，而 `SET NOT NULL` **拦不住空串**
⇒ **迁移"成功"了，数据是垃圾的**，要等线上"某个员工看不见自己的员工"才发现。

**⇒ 动手前必须先跑（只读）**：

```sql
SELECT count(*) FROM workbench_digital_employees WHERE created_by IS NULL OR created_by = '';
SELECT count(*) FROM workbench_digital_employees WHERE created_by <> owner_user_id;  -- 回填后核对
```

若第一条 > 0 ⇒ **不能直接照抄 B1 的 UPDATE**，要先决定兜底归属或先清脏数据。
