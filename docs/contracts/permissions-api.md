## 1. 接口清单（实测）

| 方法 | 路径 | 请求 | 响应 | 角色要求（实测） |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/workforce/roles` | `status`（可选 `active`/`disabled`）、`limit`（1–200，默认 50）、`offset`（≥0） | `{ items: JobRole[], total, limit, offset }` | **仅 `super_admin`**（非超管 `403`） |
| GET | `/api/v1/knowledge-access/roles/{role_key}` | 路径参数 | `{ binding_type: "role", binding_key, knowledge_base_ids: string[] }` | 仅 `super_admin`（`403`） |
| PUT | `/api/v1/knowledge-access/roles/{role_key}` | `{ knowledge_base_ids: string[] }`（`extra="forbid"`、**≤100 项**） | 同 GET（写入后的实际值） | 同上；**未纳管标识 ⇒ `409`** |
| GET | `/api/v1/knowledge-access/agents/{agent_key}` | 路径参数 | `{ binding_type: "agent", binding_key, knowledge_base_ids: string[] }` | 同上 |
| PUT | `/api/v1/knowledge-access/agents/{agent_key}` | 同上 | 同上 | 同上 |
| GET | `/api/v1/knowledge-access/audits` | `limit`（1–500，默认 100） | **数组**：`{ tenant_id, binding_type, binding_key, old_knowledge_base_ids, new_knowledge_base_ids, actor_id, occurred_at }` | 仅 `super_admin`（`403`） |

`JobRole` 逐键点名：`role_key`（标识，**不可改**）、`name`（中文名）、`description`、`status`（受控枚举 `active` / `disabled`）、
`created_by`、`created_at`、`updated_at`（后三者可为 `null`）。

## 2. 错误码与界面处置（**实测原文**）

| 场景 | 状态码 | 服务端原文 | 界面处置 |
| --- | --- | --- | --- |
| 非超管读写 | `403` | `{"detail":"只有超级管理员可以调整知识库范围"}` | 整页**无权限态**（列表不渲染编辑控件）；操作时二次失败 ⇒ 就地 Alert |
| 写入未纳管标识 | `409` | `{"detail":"该标识尚未纳入目录，请先在「数字员工设置」中纳管"}` | 抽屉内 Alert + **不关闭抽屉、不假装成功**（服务端**零写入**，实测） |
| 请求体含未知字段 / 非法值 | `422` | `detail` 是**数组**（`extra_forbidden` 等） | `safeDetail` 只接受**字符串** ⇒ 落回本地固定文案，**绝不渲染原始校验 JSON** |
| 未登录 / 令牌失效 | `401` | — | 由统一请求层清会话并回登录页（批 1 口径） |

**顺序语义（实测）**：写路径**先判权限、后判目录** —— 员工对未纳管标识 PUT 得到的是 `403` 而不是 `409`。

## 3. 页面契约（三块，一页承载）

| 块 | 数据来源 | 交互 | 空态口径 |
| --- | --- | --- | --- |
| **角色知识范围** | `workforce/roles` + 每行 `knowledge-access/roles/{key}` | 行内「编辑范围」⇒ 抽屉（候选 + 手动录入）⇒ PUT ⇒ 刷新该行 | 目录里没有角色 ⇒ 「目录里还没有岗位；请先在「数字员工设置」中纳管」+ 说明（**不显示"0 条绑定"冒充内容**） |
| **数字员工知识范围** | `workforce/agents`（批 2 契约）+ `knowledge-access/agents/{key}` | 同上 | 同上（文案换成数字员工） |

**四态**：加载 / 空 / 错误（可重试）/ 无权限；**无权限**用整页 `PermissionGuard` 呈现，**不渲染任何编辑控件**。

## 4. 候选知识库标识的来源

**现行口径（2026-09-21 · 第 15 轮改写；专项契约 `permissions-fake-entry-plan.md` B2′）**：

- **候选 = 上游知识库清单 ∪ 本租户已绑定标识**：新增只读端点 `GET /api/v1/knowledge/bases`
  （判定与知识范围写路径同一闸门：`ceo` + `super_admin`；`403` 在上游动作**之前**判定）返回
  `{upstream_available, source, items[{knowledge_base_id, name, origin}], note}`；
  `origin="upstream"` = 上游清单里真有，`origin="binding_only"` = 只在本租户绑定里出现过
  （这正是"标识写过但上游查不到"的**可见化**，界面据此给**不阻断的黄色提醒**）。
- **降级不谎报**（非协商口径）：上游不可用时 `upstream_available=false` + `source="local_only"` +
  `items` = 本租户绑定并集 + `note` 写明原因（未配置服务 / 超时 / 服务暂不可用 / 返回内容无法识别）；
  **绝不返回空数组冒充"没有知识库"**。前端在 `source="local_only"` 时按"降级"呈现并保留手输。
- **手动录入必须保留**（否则从未绑定过的租户永远无法完成第一次绑定 ⇒ 死锁）；界面固定文案
  `CANDIDATE_NOTE`：「候选来自知识库清单；也可直接输入标识 —— 平台无法校验标识是否存在，请与知识库的实际标识保持一致。」
- 前端校验**只有**：非空、去重、**≤100 项**（服务端 `max_length=100`）；**服务端仍是唯一权威**
  （前端不预设合法性；平台**不校验标识存在性**，写错仍会保存成功）。
- ⚠️ 上游 `GET /api/v1/knowledge-bases` **当前为「未实调」**（本机无可用上游实例/凭据；形状取自上游公开官方文档，
  多键兼容解析 `id|knowledge_base_id|kb_id` 与 `name|title`）。**不得**把它读成"上游已对接验证"。

## 8. 实施落地口径（写码后回写）

| 项 | 落地口径 |
| --- | --- |
| 请求层 | 全部走 `src/api/client.ts`；写路径用 `PUT`（见上 §6 的收窄说明，未改 `api/**`） |
| 取数 | 目录 `limit=200&offset=0` 一次取满；**逐行** `GET` 该行绑定（后端无批量接口）⇒ 请求数 = `1 + 行数`；`total > items.length` 直接抛错（不展示残缺数据） |
| 行状态 | 未知 `status` 抛错（**不误标**成"已启用 / 已停用"）；绑定形状不符（缺 `knowledge_base_ids`）也抛错（**不默认成"未绑定"**） |
| 失败分类 | 读：`403 → forbidden`，其余 `failed`；写：`403 → forbidden`、`409 → conflict`、`422 → invalid`、其余 `failed` |
| 候选 | **2026-09-21 第 15 轮改写**：`listKnowledgeBases()` 取 `GET /api/v1/knowledge/bases`（打开抽屉才请求）；降级/加载/失败四态见 §4；`unknownCandidateIds()` 只把 `origin="upstream"` 当"清单里真有"，其余给黄色提醒（**不阻断**）；界面允许手输；固定文案 `CANDIDATE_NOTE`（旧 `collectCandidates` 已删除） |
| 前端校验 | 空项拒绝 / 去重 / **≤100**；**留空合法**（= 解除该对象全部绑定）——合法性一律以服务端为准 |
| 写成功 | 用**服务端回读值**提示（数量取 `binding.knowledge_base_ids.length`）+ `invalidateQueries` 刷新该块与变更记录 |
| 写失败 | 就地 Alert（服务端原文 + 「本次没有写入任何数据」），**不关闭抽屉、不假装成功** |
| 样例模式 | `written = false` 且 `binding = null`（**不伪造回读值**）；不触发刷新（没有可刷新的服务端变化） |
| 无权限 | 整页 `PermissionGuard`（能力 `permission.manage`）⇒ 不请求数据、不渲染任何编辑控件 |

**③ 传输层原文取证（区分"超时中止"与"连接被拒"的唯一硬证据）**

界面在两种触发下**完全一致**（见 ④），故触发差异只能靠浏览器网络/控制台原文区分。以下为控制台原文**逐字**摘录：

| 触发 | 原文（三条取数请求） |
| --- | --- |
| 超时中止（12s 延迟） | `net::ERR_ABORTED http://127.0.0.1:18139/api/v1/workforce/roles?limit=200&offset=0`、`net::ERR_ABORTED …/workforce/agents?limit=200&offset=0`、`net::ERR_ABORTED …/knowledge-access/audits?limit=20` |
| 真实网络中断（杀进程） | `net::ERR_CONNECTION_REFUSED http://127.0.0.1:18139/api/v1/workforce/roles?limit=200&offset=0`、`net::ERR_CONNECTION_REFUSED …/workforce/agents?limit=200&offset=0`、`net::ERR_CONNECTION_REFUSED …/knowledge-access/audits?limit=20` |

**旁证（如实登记，不读成产品缺陷）**：走查者从页面上下文调走查后端的模式开关时，控制台记为
`net::ERR_FAILED http://127.0.0.1:18139/api/__r19/mode?set=slow&delay=12` —— 走查后端的控制端点**不带 CORS 响应头**，
浏览器能发出请求、服务端**副作用已生效**（随后用 `curl` 读 `GET /api/__r19/mode` 得 `{"mode":"slow"}` 证实），
但 JS **读不到响应** ⇒ 报网络错、`fetch` 返回 `undefined`。这是**走查脚手架**的性质，**与产品代码无关**。

**④ 本轮最重要的发现（如实登记，**不擅自改**）**：取数失败的界面文案取的是**各块固定文案**
（`PermissionsPage.STATE_TEXT[kind].error`），**不渲染请求层已 sanitize 的 `message`** ⇒
①逐字节相同的截图（`r19-02a/02b/02c` 与 `r19-05a/05b/05c-outage-*` 的 SHA-256 前 12 位**两两相同**：
`DA9FF514D403` / `1DD7236C55C0` / `A9DBA2DA8E9F`，即同一渲染结果）与 ②网络层原文（`ERR_ABORTED` vs `ERR_CONNECTION_REFUSED`）
共同说明：**"客户端超时中止"与"真实网络中断"在界面上不可区分**（都只是"加载失败，请稍后重试"）。
是否需要让读侧也区分这两种原因（或把请求层文案上屏），属**产品口径变更** ⇒ **列为本轮待裁决项，未动手**。
