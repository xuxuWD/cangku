# 知识库 ACL 规则（唯一权威）

> 状态：**草案 v1 · 2026-09-19**（第 0 轮交付物）。依据：《PRD》§5.3（KB-01~KB-05）、《开发设计规则》§4.3、
> 《启动准备清单》§二.2（文档 ACL 标签体系）与仓库实测现状。
> 本文件是知识库可见性口径的**唯一权威**；变更必须回写本文件。配套：`permission-matrix.md`、`role-templates.md`。

## 1. 四级标签（定死）与逐级权限

| 级别 | 键 | 谁能看 | 谁能改 / 发布 | 能否导出 | 数字员工可否检索 |
| --- | --- | --- | --- | --- | --- |
| 公开 | `public` | 本租户全部角色 | 知识管理员（`ceo` / `super_admin`）+ 负责人 | ✅ | ✅ |
| 内部 | `internal` | 有**库级绑定**的角色 / 员工 | 同上 | ✅ | ✅ |
| 机密 | `confidential` | 有库级绑定 **且** 角色 ∈ {`department_lead`, `ceo`, `super_admin`} 或**显式点名授权** | 同上 + 负责人本人 | ⚠️ 仅 `super_admin`，且写审计 | ✅（以**创建者权限**为准，见 §5） |
| 绝密 | `restricted` | 仅**显式点名授权**的账号（角色不足以自动获得） | 仅 `super_admin` + 负责人 | ❌ 禁止导出（接口拒绝） | ⚠️ 默认不可，需显式授权到**该数字员工** |

> 与 PRD 一一对应：公开 / 内部 / 机密 / 绝密。

## 2. 两层过滤模型（**先库、后文档**，缺一不可）

```
第 1 层（库级绑定，现状已有）：谁能进哪些知识库 —— 知识访问绑定（角色 / 员工 ↔ 知识库），无绑定即不可见
第 2 层（文档级 ACL，本轮新增）：进了库之后，库内**每个文档**按 §1 分级二次判定
最终可见 = 第1层命中 ∧ 第2层命中 ∧ 治理状态可用
```

**关键约束**：两层都必须**在检索请求前**完成判定；**不允许**"先检索全部、再在生成后删除"（规范明令禁止"生成后补救"）。

## 2.5 知识角色与能力映射（**唯一来源**）+ 职责分离

除"四级标签"外，库内**操作权**由**角色 → 能力**的映射表决定（不是按级别硬编码），且该映射表是**唯一来源**——任何"例外放行"都不允许绕过它。

| 能力（示例键） | 含义 | 说明 |
| --- | --- | --- |
| `INGEST` | 入库 / 提交资料 | 提交者 |
| `READ_METADATA` | 读元数据（标题/分类/状态） | 最低可见档 |
| `READ_RAW` | 读**原文/原件** | 高于读元数据 |
| `REVIEW_PARSE` | 解析结果复核 | 审核权 |
| `CLASSIFY` | 分级定级 / 改级 | 定级权 |
| `VERIFY_FACT` | 事实核验 | **不得与提交者同一人** |
| `REVOKE` | 撤回已发布内容 | **不得与提交者/核验者同一人** |

**职责分离（四眼原则，定死）**：`提交 ≠ 核验 ≠ 撤回`，三者不可由同一账号在同一条资料上完成；每一次越界尝试都要被服务端拒绝并写审计。
**一人一角色约束**：同一人在同一项目内只应持有一个知识角色（映射表侧加唯一性约束），避免"叠加角色 = 隐性提权"。

> 依据：`D:\徐徐AI学习\AI知识库\raw\sources\GEO\GEO-WeKnora检索适配器PoC设计规格-2026-09-06.md`（原文：「具体能力以现有 `evidence_hub_permissions` 映射为唯一来源」；四类可调用角色 = `tenant_admin` / `evidence_reviewer` / 有项目授权的 `contributor` / 有效期内内部支持）。

## 3. 过滤执行层（定死：服务端检索谓词）

| 项 | 规则 |
| --- | --- |
| 执行位置 | 服务端**检索守卫**（现状：`POST /api/v1/knowledge/search` 的前置守卫，fail-closed） |
| 谓词 | `tenant_id = 上下文租户` ∧ `文档已登记` ∧ `status = published` ∧ `acl_level ∈ 允许集合(用户)` ∧ `库级绑定命中` |
| fail-closed | 无绑定 / 无该级别授权 / 文档未登记 ⇒ **返回空结果并写审计**（禁止放开、禁止返回他人文档）；**空集不得请求上游检索**（省掉一次越权可能） |
| 禁止"先取后补" | 所有资源查询**必须带过滤条件**；**不得**"先按资料 ID 取回、再补做项目/级别判断"（原文：「不能先按语句 ID 取资源后再补项目判断」） |
| 废弃/待复核 | `archived`、`needs_review`、`under_review`、`draft` **一律排除**（沿用现有状态机口径） |
| 无权限提示 | 界面必须呈现"无权限"态，而不是"没有资料"（避免用户误判） |
| 查询留痕 | 审计只记**结论与键**（`role_key` / `agent_key` / `reason`），**不记查询正文**（个人信息的既有口径） |

## 4. 与现有数据分级（`DataClassification`）的映射（定死，二义性零容忍）

现状 `app/agent_services.py` 的 5 级用于**模型路由**（数据出境与模型选择），**不是**文档 ACL。两者并存但必须显式映射：

| 现有 5 级（模型路由） | 对应 ACL（文档可见性） |
| --- | --- |
| `public` | 公开 |
| `internal` | 内部 |
| `confidential` | 机密 |
| `sensitive` | 绝密 |
| `restricted` | 绝密 |

> 规则：**模型路由级别只升不降**——当文档 ACL = 绝密时，路由级别不得低于 `restricted`；
> 即"模型选择"与"谁能看"是两件事，但绝密数据不得被路由到低保障模型（此约束写入模型网关与执行链路的测试）。

## 5. 数字员工检索（KB-05 定死）

1. 数字员工检索时使用的权限 = **创建者权限 ∩ 使用者权限 ∩ 岗位能力包**（见 `permission-matrix.md` §2.3）；
2. **共享不提升可见范围**：A 创建的数字员工被共享给 B 后，检索范围 = A ∩ B，**不会**因为 B 权限更高而看到 A 看不到的文档；
3. 绝密文档要能被某数字员工检索 ⇒ 必须**显式授权到该数字员工**（不是授权给使用者）；
4. 每次检索都走 §3 的同一谓词（不允许"创建者权限缓存后放宽"）。

## 6. 输出与溯源（沿用现状，写入契约）

- 所有基于知识库的回答**必须携带来源引用**（文档标识 + 标题 + 定位信息）；无引用的结论不得入库到任务产出；
- 引用不得泄露宿主路径 / 内部地址 / 凭据（沿用既有脱敏口径）。

## 7. 差距与落地项（本轮只登记）

| 缺口（实测） | 落地项 | 归属轮次 |
| --- | --- | --- |
| 文档表**无 ACL 字段**（`workbench_knowledge_documents` 仅 title/owner/status/version/source_key/复核时间） | 加 `acl_level` 列（枚举 4 值）+ 默认值策略 + 历史数据归类 | 第 1 轮 |
| 检索入口**仅 `super_admin` 可用** | 放开到"有绑定 + 级别授权"的角色/员工 | 第 1 轮 |
| 无"显式点名授权到人/到员工"的载体 | 复用/扩展知识访问绑定，增加 `principal_type`（角色/账号/数字员工）+ `max_acl_level` | 第 1 轮 |
| 绝密"禁止导出"无实现 | 导出路径加级别拒绝 + 用例 | 第 1 轮 |
| 前端无"无权限"态 | 组件库阶段统一（八态之一） | 第 2 轮 |

## 8. 验收（可验证语句）

1. 用无绑定的账号检索：返回**空结果**且审计有记录（不是 500，也不是他人文档）。
2. 绑定了「内部」库、但文档标 `confidential` 的用户检索：**不返回**该文档。
3. `restricted` 文档被授权到数字员工 X、未授权到员工 Y：Y 用 X 代跑也**取不到**该文档。
4. 绝密文档导出请求 ⇒ 接口拒绝（含 `403` 语义），且写审计。
5. 任一检索**不产生**"先取回全部再过滤"的调用（可用上游请求参数与日志核对：谓词在请求前生效）。
