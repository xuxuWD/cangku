## 2. 问题清单

> **本批原报**：P0 = 0；**P1 = 1**；**P2 = 6**；P3 = 0。
>
> **⚠️ 2026-09-18 更正：原 C-01「删除会话无二次确认」为误判。**
> 复核证据：`admin-web/src/features/conversation/ConversationPage.tsx:369-373` 存在 `globalThis.confirm?.(…)` 且 `confirmed === false` 时直接 return。
> 实测证据：**先把对话框预置为 `dismiss` 再点「删除会话」** ⇒ 删除**不发生**（URL 保持 `?view=conversation&conversation=conv-192a94806469`，会话内容区仍显示「共 0 条消息 / 这个会话还没有消息」）。
> ⇒ **确认对话框确实存在。** 原判「无确认」的原因是：**自动化框架会自动接受原生对话框**，我未察觉这一行为，把"自动接受"误读成了"没有弹窗"。
> **更正后计数：P0 = 0；P1 = 0；P2 = 7；P3 = 0**（C-01 由 P1 降为 P2，与 C-02「混用原生 confirm」合并为同一根因）。
>
> **方法论教训（已纳入本项目的证据纪律）**：凡是**原生对话框**（`confirm` / `alert` / `prompt`）相关的结论，必须**先预置对话框行为（accept / dismiss）再触发操作**，并**用"操作是否发生"反向验证对话框是否存在**；直接观察"有没有弹窗"会因自动化框架的默认行为而失真。

### C-01 【原 P1 → 更正为 P2】删除会话**有二次确认（浏览器原生 confirm），但不可撤销**

> **本条初版为误判，已更正**：确认对话框**存在**（`ConversationPage.tsx:369-373` 的 `globalThis.confirm?.(…)`，且 `confirmed === false` 时直接 return）。下表按更正后的口径重写。**真正的问题从"没有确认"变为"用的是原生 confirm + 无撤销"**（与 C-02 同根因）。

| 字段 | 内容 |
| --- | --- |
| 模块 / 页面 | 对话页 · 会话内容区 |
| 用户角色 | 全部 |
| 问题 | 删除会话使用**浏览器原生 `window.confirm`** 做二次确认（样式与文案不受产品控制），且确认后为**物理删除、无撤销**。 |
| 复现步骤 | ① 打开 `?view=conversation` → ② 点「新建会话」进入新会话 → ③ 点「删除会话」 → ④ 立即观察页面（不做任何确认动作） |
| 实际结果 | ① **有**二次确认 —— 但为**浏览器原生 `window.confirm`**（初版所称"无确认"**为误判**）<br>② 确认后立即**物理删除**且**无撤销**<br>③ 删除后提示为技术计数「已删除（消息 n / 帧 n / 流状态 n / 幂等 n）」 |
| 预期结果 | 破坏性且不可恢复的操作，应使用**产品内确认组件**（说明后果 + 危险操作视觉隔离 + 可 Esc 取消），并尽量提供撤销窗口 |
| 证据 | **① 反驳初版（证明对话框存在）**：预置 `handle_dialog({action:'dismiss'})` 后点「删除会话」⇒ **删除未发生**（URL 保持 `?view=conversation&conversation=conv-192a94806469`；内容区仍显示「共 0 条消息 / 这个会话还没有消息」）<br>**② 支持本条（确认后不可撤销）**：确认被执行时删除立即生效，URL 变为 `?view=conversation`，提示「已删除（消息 0 / 帧 0 / 流状态 0 / 幂等 0）」<br>**③ 代码证据**：`ConversationPage.tsx:369-372` 确认文案原文「删除后：本会话的消息、过程帧、流状态与幂等记录会被物理删除（**不可撤销**，仅本人会话）；会话标题会清空，运行记录与审计按合规口径保留。确认删除？」 |
| 影响 | 排查文件 C 组要求「确认**和**撤销」——**确认有、撤销无**，属**半满足**。误点 + 误确认即永久失去整段会话与产出记录；原生 `confirm` 无法承载危险操作的视觉隔离与品牌一致性 |
| 整改建议 | ① 改为**产品内确认对话框**（说明将删除什么、是否可恢复）；② 提供撤销窗口（如 5 秒内可撤销）或改为"移入回收站"；③ 危险按钮与主按钮视觉隔离 |
| 验收标准 | 点删除必先出现确认；确认文案说明后果；删除后 5 秒内可撤销；键盘 Esc 可取消确认 |
| 工作量 | 中 |
| 依赖 | 需先定"物理删除 vs 软删除 + 保留期"口径（与 P2c-4 既有裁决相关） |

### C-02 【P2】确认类操作混用**浏览器原生 `confirm`**

| 字段 | 内容 |
| --- | --- |
| 模块 / 页面 | 内容工作台 · 导出确认 |
| 用户角色 | 内容岗 |
| 问题 | 使用 `window.confirm('确认内容已完成自检并导出？')` 这类**浏览器原生弹窗**。 |
| 复现步骤 | 代码证据：`admin-web/src/features/contentWorkbench/ContentWorkbenchPage.tsx:72` |
| 实际结果 | 确认弹窗外观由浏览器决定，与产品设计语言完全脱节；无法展示"导出的是什么/导出到哪/能不能撤销"；无法承载危险操作样式 |
| 预期结果 | 统一的产品内确认组件（说明后果 + 主次按钮 + 可 Esc 关闭） |

| 验收标准 | 全仓无 `window.confirm`/`window.alert`；确认弹窗为产品内组件；Esc 可关、焦点受管 |
| 工作量 | 小 |
| 依赖 | 无 |

## 6. 本批小结

- **P0 = 0**；**P1 = 0**；**P2 = 7**（**已按 §2 更正**）。
- **本批无 P1**：原报的 P1「删除会话无确认」经复核**为误判** —— 确认**存在**（原生 `window.confirm`）。真正的问题降级为 P2：**原生 confirm + 物理删除 + 无撤销**。整改建议不变（产品内确认组件 + 撤销窗口/回收站）。
- **本次误判的方法论教训**（比问题本身更重要）：**自动化框架会自动接受原生对话框**，因此「没看到弹窗」**不能**推出「没有确认」。凡对话框类结论，必须**先预置 accept / dismiss，再用"操作是否发生"反向验证**。
- **最有价值的正面发现是 G-06**：后端起不来时的错误态（分区独立 + 人话文案 + 重试按钮）**已经达到排查文件的要求**，应作为其他页面错误态的模板，而不是推倒重做。
- **两处系统性根因**（多处问题共享）：
  1. **把交互交给浏览器原生**（`confirm` 弹窗、`required` 校验）⇒ C-02 / C-03；
  2. **开发视角文案泄漏到用户界面**（stub / 幂等键 / 九步闸门 / 帧 / 流状态）⇒ C-04 / C-05（及批 1 的 IA-04）。
