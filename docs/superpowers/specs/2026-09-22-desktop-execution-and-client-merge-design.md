## 0. 一句话

把执行端从「只有服务端容器」改为「**桌面 + 服务端并存**」——但**用户、权限、审计三者仍只有服务端一套真源**；同时把 4 个客户端收敛为「**1 份前端产物 + 2 种投递**」。

## 1. 为什么能做（对 L51 的精确解读）

`architecture.md` 现行条文的原文是：

> **一类明确不可搬的（硬约束）**：把「**用户本机 CLI 当引擎 / 单机单用户**」形态的 harness 搬进来，会带进**第二套用户、权限与审计**，并与本节「发布边界」「自动化与权限」冲突。

**关键解读（本节是修订的前提，必须先说清）**：

| 项 | 原文的约束对象 | 是否等于"禁止自己的桌面端做执行端" |
| --- | --- | --- |
| **「搬进来」** | **别人的** harness 源码进本仓库 | ❌ 不等——用户方案**不搬任何代码** |
| **「单机单用户」** | 那种形态**假设只有一个用户** | ❌ 不等——用户方案的**用户仍是服务端多租户的** |
| **「会带进第二套用户、权限与审计」** | **这是真正的反对理由** | ✅ **完全适用**——桌面执行若自带权限判定与本地审计，就是第二套 |

**⇒ 结论：L51 反对的不是「桌面执行」，而是「桌面执行附带第二套用户/权限/审计」。**

**而本轮裁决恰好消除了后一条**：

> **审计只有一套、落在服务端**（D-050④）——桌面执行时闸门可灵活，但**审计必须回传**。

**⇒ 因此允许的形态是**：「**桌面作执行端 + 用户/权限/审计单源在服务端**」——这是对 L51 的**收窄放开**，不是删除。修订稿见 §5。

## 2. 执行模型：桌面 + 服务端并存

### 2.1 任务分流判据（唯一判据）

**判据只有一条**：**该任务是否需要「本机能力」**。

| 需要本机能力 ⇒ **桌面执行** | 不需要 ⇒ **服务端容器执行** |
| --- | --- |
| **用户登录态的浏览器**（会话在用户机器上） | 知识检索（WeKnora / 自有库） |
| **本地文件读写**（用户工作区） | 文档生成 / 解析（无本机依赖） |
| **本机命令 / 终端** | 模型调用 / 推理 |
| **本机硬件**（截图、摄像头、设备） | 定时任务、批量计算 |
| **需要用户当场介入**的操作 | 外部 API 调用 |

**⚠️ 反向约束（同样重要）**：**不需要本机能力的任务，禁止走桌面**。理由：桌面执行的可审计性弱于容器（见 §2.2），**能走容器就走容器**。

**⚠️ 不得按「用户偏好」分流**——分流是**服务端判定**的，不是客户端自选的。客户端只能**请求**，不能**决定**。

### 2.2 ⭐ 审计单源机制（本文的核心）

**铁律：`app/audit/` 是唯一审计真源。桌面执行产生的记录，必须回到它。**

**三阶段回传模型**：

```
① 授权（执行前）
   桌面 → 服务端：POST /api/v1/execution/authorize
   服务端：跑闸门判定（白名单 / schema / 风险定档 / 授权位）
   服务端 → 桌面：短期执行令牌（含授权范围、有效期、幂等键）
   ★ 桌面不自行判定权限——它只执行服务端给出的决定

② 执行（进行中）
   桌面：按令牌范围执行
   桌面 → 服务端：POST /api/v1/execution/{id}/events（异步、可批量、可缓冲）
   ★ 事件是"过程记录"，允许延迟与合并；丢失不致命

③ 结算（执行后）
   桌面 → 服务端：POST /api/v1/execution/{id}/settle（审计摘要，必须成功）
   服务端：写 audit（一次性、幂等）
   ★ 这是唯一**必须成功**的回传；失败则任务标记为「未结算」
```

**关键设计决定**：

| 决定 | 理由 |
| --- | --- |
| **令牌制（短期、限定范围）** | 桌面不持有长期凭据；令牌过期即失效 |
| **①②③ 三段分离** | 过程可丢、结论不可丢——**审计要求的是结论完整，不是过程完整** |
| **结算失败 ⇒ 标记「未结算」** | 不假装成功；未结算的任务在界面上显式可见 |
| **幂等键贯穿三段** | 防重复授权、重复结算 |

### 2.3 断网处理（三选一，**建议 B**）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 断网期间本地暂存，恢复后补传 | **审计有空窗期**——空窗内的操作无法被覆盖 |
| **B（建议）** | **断网期间不允许执行"需结算"的动作** | 断网时降级为只读；用户体验略差 |
| C | 断网期间完全禁用桌面执行 | 最保守，但断网即不可用 |

**建议 B 的理由**：审计单源是铁律，而 A 的空窗期意味着**无法回答"断网期间那台机器上发生了什么"**——这恰好是审计要防的事。

**B 的具体口径**：
- 断网 ⇒ 桌面进入**只读模式**（可看历史、可浏览，不可执行需结算的动作）
- 断网期间的本地操作**不入账**、**不产生副作用**
- 恢复后由用户手动重试

### 2.4 九步闸门怎么拆

**服务端任务**：九步闸门**完全不变**。

**桌面任务**：闸门**按"判定 / 执行 / 记账"三分**——

| 步 | 内容 | 落在哪 |
| --- | --- | --- |
| ① 白名单 | 工具面校验 | **服务端** |
| ② 参数 schema | 结构校验 | **服务端** |
| ③ realpath 路径 | 路径解析 | **服务端**（用服务端的工作区视图） |
| ④-0/1/2 | 红线 / 敏感路径 | **服务端** |
| ⑤ 风险定档 | 四档 | **服务端** |
| ⑥ 落库待批 | `needs_approval` | **服务端** |
| ⑦ 逐项授权 | 授权位 | **服务端** |
| ⑧ 执行 | 实际动作 | **桌面**（服务端任务则仍在容器） |
| ⑨ 摘要 + 审计 | 落 audit | **服务端**（桌面回传，见 §2.2） |

**⇒ 即：闸门的「判定」与「记账」永远在服务端，只有「执行」这一步落到桌面。**

**⚠️ 待评审的一个缺口**：第 ③ 步（realpath 路径）在桌面执行时，**服务端看到的工作区视图与桌面实际视图可能不一致**（服务端的路径解析基于服务端挂载，桌面基于用户机器）。**这是本文识别的最大技术风险**，见 §6 R1。

### 2.5 桌面端的权限边界（防「第二套」的三条闸门）

| # | 约束 | 验证方式 |
| --- | --- | --- |
| **D1** | 桌面**不自行做任何权限判定**——只执行服务端令牌内的范围 | 桌面代码里不出现角色/权限比较 |
| **D2** | 桌面**不持有长期凭据**——只用短期执行令牌（有效期由服务端定） | 令牌过期后桌面无法自行续期 |
| **D3** | 桌面**不落独立审计**——只做上报；本地日志仅供排障，**不作为事实源** | 服务端审计里能查到桌面上发生的每一次执行 |

## 3. 数据模型：`Agent` / `Assignment` 两层

### 3.1 现状与缺口（实测）

| 缺口 | 证据 |
| --- | --- |
| **无归属人** | 迁移 `022_workforce_directory.sql` 只有 `created_by`，**无 `owner_user_id`** |
| **无共享机制** | 无成员表；前端只能用「我创建的 / 共享给我的 / **归属无法判定**」三分区容错 |
| **目录接口仅超管** | 前端注释：`` http 模式下无权限是后端真实口径（该目录接口仅超级管理员） `` |
| **无员工侧创建接口** | 前端注释：`从岗位模板创建（DE-01）：本批未接入（后端无员工侧创建接口）` |
| **无岗位模板** | 6 类岗位无预置种子 |

### 3.2 为什么必须两层（而不是加一列）

**加一列不够**，因为要同时回答两个正交问题：

- **「这个数字员工是谁」**（能力包：角色 / 模型 / 工具 / 技能 / 记忆策略）——**可复用、可模板化**
- **「这个数字员工归谁、谁能用、什么时候上班、要谁批」**（归属合同）——**per 人 per 岗，不可复用**

**⇒ 若合成一张表**：同一个能力包被多人使用时，归属字段会互相覆盖。
**⇒ 两层后**：能力包（`Agent`）一份，归属合同（`Assignment`）多条，**一份能力可被多人各自持有而不冲突**。

### 3.3 建议的模型（字段级）

**① 改 `workbench_digital_employees`（能力包层，保留现有字段）**

```sql
ALTER TABLE workbench_digital_employees
  ADD COLUMN IF NOT EXISTS visibility TEXT NOT NULL DEFAULT 'private'
    CHECK (visibility IN ('private', 'shared'));
-- owner_user_id 见下：存量行回填 created_by
ALTER TABLE workbench_digital_employees
  ADD COLUMN IF NOT EXISTS owner_user_id TEXT;
UPDATE workbench_digital_employees SET owner_user_id = created_by WHERE owner_user_id IS NULL;
ALTER TABLE workbench_digital_employees ALTER COLUMN owner_user_id SET NOT NULL;
CREATE INDEX IF NOT EXISTS idx_wde_owner ON workbench_digital_employees (tenant_id, owner_user_id);
```

> **注**：现有 `role_key`（复合外键指向 `workbench_job_roles`）**保留不动**——它是"岗位"，与 owner 正交。

**② 新增 `workbench_employee_shares`（共享层，照抄 P2c-6 会话成员表的两档模式）**

```sql
CREATE TABLE IF NOT EXISTS workbench_employee_shares (
  tenant_id       TEXT NOT NULL,
  agent_key       TEXT NOT NULL,
  grantee_user_id TEXT NOT NULL,
  permission      TEXT NOT NULL CHECK (permission IN ('read', 'use')),
  granted_by      TEXT NOT NULL,
  granted_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, agent_key, grantee_user_id),
  FOREIGN KEY (tenant_id, agent_key)
    REFERENCES workbench_digital_employees (tenant_id, agent_key)
);
```

| 档 | 含义 |
| --- | --- |
| `read` | 能看配置、看它干过的活；**不能派活** |
| `use` | 能派活；**不能改配置、不能停用** |

> **口径对齐**：与 P2c-6 的会话成员表 `read`/`write` **同款两档语义**（改名 `use` 以贴合"派活"而非"发言"）。**这是刻意的复用**——用户已经有一套成员表心智模型，不引入第二套。

**③ 岗位模板（新增配置，不必建表）**

6 类岗位模板建议放**代码内常量**（`app/workforce/role_templates.py`），理由：模板是**产品预设**而非用户数据，改模板应走代码评审而非 DB 更新。

每套模板字段：`role_key` / `display_name` / `soul_md`（气质/价值观）/ `system_prompt`（步骤/边界）/ `default_tool_allowlist` / `default_skills` / `default_autonomy_level`。

**④ 目录查询的权限口径（三档可见性）**

```
可见 = owner_user_id = 我                      （我创建的）
     ∪ 在 workbench_employee_shares 里          （共享给我的）
     ∪ (visibility = 'shared' AND role_key ∈ 我的岗位)   （岗位共享，可选档）
     ∪ 我是 super_admin                          （管理视角）
```

**⇒ 这一条直接修掉「普通员工看到 403」**。

### 3.4 迁移的影响面

| 影响 | 处置 |
| --- | --- |
| 存量行 `owner_user_id` | 回填 `created_by`（无条件、可重跑） |
| 存量行 `visibility` | 默认 `private`（**最保守**——不因迁移而扩大可见性） |
| 目录接口 | 从"仅超管"改为 §3.3④ 的四档口径 —— **这是行为变更，须在契约里写明** |
| 前端三分区 | 「归属无法判定」分区**可以撤掉**（不再需要容错） |

### 修订 2：§客户端 — 四端收敛

**现文**（B0 刚补的）：
> 四端都只调用版本化 `/api/v1`，不直连数据库；……
> ⚠️ **`admin-web` 与 `workbench-web` 的职责收敛属未决项**……

**建议改为**：
> **目标形态：1 份前端产物 + 2 种投递**（桌面内嵌为主 / 浏览器仅管理远程）——见 `docs/superpowers/specs/2026-09-22-desktop-execution-and-client-merge-design.md` §4。
> **⚠️ 收敛**未执行**，现仍为 4 个独立客户端；逐模块归属表见该规格 §4.2（待裁决）。

### 修订 3：§发布边界

**现文**：
> 优先使用官方 API；无官方 API 时使用用户本人登录的本地授权助手；无法确认授权路径时只提供人工交付内容包。系统不保存密码、Cookie、验证码或会话快照，也不实现私有接口模拟、风控规避、设备伪装和代理轮换。

**建议**：**本节本轮不改**。理由：桌面执行不改变发布边界的实质约束（见 §6 R3——反检测是**另一条独立的评审**，不与本规格捆绑）。

### 修订 4：§自动化与权限

**建议增补一段**：
> **执行端与闸门的关系（2026-09-22）**：用户、权限、审计三者**只有服务端一套真源**；桌面执行端**不自行判定权限、不持有长期凭据、不落独立审计**（三条闸门见执行模型规格 §2.5）。任务分流由**服务端判定**，客户端只能请求、不能决定。
