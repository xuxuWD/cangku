## 2. 目标形态

```
┌──────────┬──────────────────────────────┬────────────────────┐
│ 侧栏      │  主区域                       │  右栏               │
│ ≤10 入口  │  对话（常驻，切走不卸载）      │  当前业务对象        │
│          │  ★ 唯一的「创建入口」          │  可展开全屏          │
└──────────┴──────────────────────────────┴────────────────────┘
              ＋ 悬浮助手（全局常驻，路由切换不卸载）
```

**三层各自的职责**：

| 层 | 内容 | 关键行为 |
| --- | --- | --- |
| **① 侧栏** | 5 主入口 + ≤4「更多」+ **常驻最近会话列表** | 目标 ≤10 入口 |
| **② 主区域** | **对话常驻** / 其他页面**互斥显示** | 对话切走只 `display:none`，**不卸载** |
| **③ 右栏** | 当前对象（工作项详情 / 执行记录 / 审计 / 产物） | 默认简要，**可展开全屏**（展开时左对话隐藏） |
| **④ 悬浮球** | 全局助手 | 常驻右下角，**规则层不用 LLM** |

**侧栏目标结构**：

```
➕ 新建对话   ☑ 待我处理   🤖 我的数字员工   📋 工作项   📚 知识库
▾ 更多：🕐 自动化  📁 文件  🧩 扩展
────────────────────────────
⚙ 设置（弹窗）   🔔 通知   👤 账号
```

**「管理类」收进设置弹窗**：人员与岗位 · 知识权限 · 审计 · 用量与费用 · 模型 · 渠道 · 数据与资源

## 3. 为什么是「三栏 + 悬浮球」而不是别的

**三种候选形态与取舍**（本文的选型依据）：

| 形态 | 优点 | 缺点 | 判断 |
| --- | --- | --- | --- |
| **① 对话占主区域，其他入口覆盖它**（EvoFlow 式） | 实现简单；对话常驻 | **主区域被争夺**——「待我处理」和「对话」不能同时看见 | ❌ 不选 |
| **② 对话占主区域 + 其他入口开右栏**（TabTin 式） | 对话永不被覆盖；左说右看 | ⚠️ TabTin 为此花了 **92,805 行** | ✅ **选这个，但收窄**（见 §5） |
| **③ 对话是浮层/抽屉** | 主区域永远给"工作" | ❌ **对话被降级**——而"数字员工下属"的交互主要发生在对话里 | ❌ 不选 |

**⇒ 选 ②，但明确收窄范围**（§5）：**右栏只放"当前对象的简要信息 + 数字员工面板"，不做"可打开任意对象的通用舞台"**。

## 4. 对话常驻的实现机制（借 EvoFlow 的设计）

**EvoFlow 的做法**（只读研读所得，**只借设计**）：

```js
// 路由分两类
if (isChatRoute(path))  renderChatRoute(...)     // 对话
else                    renderContentRoute(...)  // 其他页

// 切走对话时 —— 隐藏，不卸载
_chatHostEl.hidden = !visible
_chatHostEl.style.display = visible ? 'flex' : 'none'
```

**它注释里写明的两个坑**（**值得直接抄**）：

> ①「**离开路由时已经 display:none；再卸列表会在标志不同步时留下永久空白**」
> ②「**必须同步**：动态 `import().then` 在快速切路由时会乱序，导致 `chatSurfaceVisible` 卡在 false」

**⇒ 本文的实现要求**：

| # | 要求 |
| --- | --- |
| **1** | 对话宿主**切走只 `display:none`、不卸载**（保 SSE 连接与滚动位置） |
| **2** | 可见性切换**必须同步**，不得放在异步回调里 |
| **3** | 需要一个 **epoch 计数器**串行化 hide/show，防快速切路由时乱序 |
| **4** | 侧栏的「最近会话列表」**与对话同一个状态树**（否则两处状态不同步） |

## 5. 右栏：**收窄，不做通用舞台**

| 项 | 决定 |
| --- | --- |
| **放什么** | 当前对象的**简要信息** + **数字员工面板**（带该对象的上下文） |
| **不放什么** | ❌ 不做"可打开任意类型对象的通用舞台" |
| **逃生口** | 需要看全屏时**展开为整页**（此时左对话隐藏，返回即回） |

**⚠️ 为什么收窄**：TabTin 的通用舞台（`context-space`）是 **92,805 行**。**本文明确不追这个规模。**

**⚠️ 右栏的上下文注入是关键**（借 TabTin 的 `agentIntegration.contextFields` 设计）：员工在某客户详情页打开数字员工面板时，**自动带上 `current_account_id`**——**而不是在空白对话框里问"帮我看看客户"**。

## 6. 悬浮窗助手

**借 EvoFlow 的 `global-assistant`**（只读研读，只借设计）：

| 机制 | 作用 |
| --- | --- |
| 挂在 `body`、**路由切换不卸载** | 任何页面都能唤起 |
| **`buildAttentionItems()`** | 跨模块统一「待你处理」清单，按 `待审批 > 待输入 > 受阻 > 失败 > 完成` 排序 |
| **`buildSuggestedActions()`** | **纯规则、不用 LLM** 的跟进建议（省钱且可测） |
| **抓当前页面上下文** | 知道"你在哪、选了什么、输入框草稿" |
| **中文正则意图路由** | `委派/交给/派给 → delegate`、`审批/待我批 → approvals` |

**⇒ 与你既有资产的衔接**：你已有 `app/conversation/`（4,113 行）与 `app/inbox.py`（站内通知收件箱）——**「待你处理」的数据源已经有了**，缺的是把它做成**常驻浮窗**。

**⚠️ 一条明确要求**：**规则层不用 LLM**。理由：待办排序与意图识别是确定性逻辑，用 LLM 只会更慢更贵更不可测。

## 7. 侧栏收敛的路径

| 步骤 | 动作 |
| --- | --- |
| **1** | **配置类收进设置弹窗**（人员/权限/审计/用量/模型/渠道…）——EvoFlow 用这一招收掉了 13 个 Tab |

| **3** | **下钻代替入口**（`runDetail` 从对话/工作项下钻，不占侧栏） |
| **4** | **归档开发期页面**（如 `components-playground`） |

**目标**：`admin-web` 17 → **≤10**；`workbench-web` 9 → 合并后**≤10 总数**。

## 8. ⚠️ 路由：两个前端**都没有**

| 现状 | 后果 |
| --- | --- |
| 两个前端切页都用**状态**（`useState`），**没有路由库** | ❌ 不能地址栏直达<br>❌ 不能分享链接<br>❌ 刷新丢状态<br>❌ 浏览器前进/后退不可用 |

**⇒ 这是"不像一个产品"的一个具体、可验收的缺口。**

**待裁决（§13.1 V2）**：引入成熟路由库 vs 自建轻量路由。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 引入 `react-router`** | 成熟、生态全、可测试 | 新依赖（须过依赖新增决策） |
| **B. 自建轻量路由** | 零依赖；与"对话常驻"的宿主机制好配合 | 要自己处理嵌套路由、参数、历史栈 |

**⚠️ 本文不预判**——但**必须解决**，否则"对话常驻 + 右栏可展开"这套交互无法正确落到 URL 上。
