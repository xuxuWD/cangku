## 3. ⭐ 外部对照：EvoFlow 的教训（本文最重要的一节）

我在拆解 EvoFlow（PolyForm Noncommercial，**只读研读**）时的核心发现：

> **它的沉淀层是一台「装配完整、仪表齐全、但没有闭环控制器」的机器。**

| 层 | EvoFlow 做到了吗 |
| --- | --- |
| ① 无条件注入 | 🟢 员工值班每班必注入 |
| ② 提示词纪律 | 🟡 `MUST prefer matching craft` —— **自然语言，可被 LLM 忽略** |
| ③ 显式引用回执 | 🟡 `<evo-asset-citation>` → `cite_count++` |
| ④ **晋升为技能** | 🟢 craft 毕业后**自动生成 SKILL.md** ← **唯一真正的硬保证** |
| ⑤ **观测** | 🔵 use_count / cite_count / hot 榜 / cold 榜**全套** |
| ⑥ **反馈闭环** | ❌ **缺失** |

**它的原话级问题**：

> 「**能告诉你这条经验被引用了 0 次，但没有任何代码因为 0 次而做任何事。**」

**⇒ 本文的设计目标因此明确为两句话**：

1. **抄它的⑤（仪表）** —— 这是把"越用越强"变成可观测指标的最小成本方案
2. **补它缺的⑥（控制器）** —— **这是你能超过它的地方**

**⚠️ 一条如实登记**：EvoFlow 里有一个**真实断点**——`bump_craft_hit()` **全仓无调用者**，导致 `hit_count` 恒为 0，晋升门控失效一半。**本文的设计必须避免同类问题**（见 §9 A5）。

## 4. 设计：计量层（抄⑤）

### 4.1 记什么

**在既有记忆/技能实体上增加四个计量字段**（不建新表）：

| 字段 | 含义 | 写入时机 |
| --- | --- | --- |
| `use_count` | **被检索命中**次数 | 检索返回时批量 `+1` |
| `last_used_at` | 最近一次命中时间 | 同上 |
| `cite_count` | **被显式引用**次数 | Agent 回执时 `+1`（见 §4.2） |
| `last_cited_at` | 最近一次引用时间 | 同上 |

**⚠️ 为什么区分 `use` 与 `cite`**：**检索命中 ≠ 被使用**——检索出来但没进最终输出，是噪声。**只有 `cite` 才接近"真的用上了"。**

### 4.2 `cite` 怎么算（本文的技术难点）

**方案：在对话链路上加一条显式回执约定**——

```
Agent 在使用某条记忆时，在输出中带一行：
  「依据：<记忆 ID 或摘要>」        ← 或等价的受控标记

服务端在解析回复时识别该标记 → cite_count++
```

**⚠️ 与 EvoFlow 的差异**：EvoFlow 用的是 `<evo-asset-citation>` XML 块。**本文建议用更轻的标记**，理由：他们的客户端是**人机界面**，标记要**人能读懂**（人要能判断 Agent 引用的对不对）。

**⚠️ 但我必须如实标注**：**这个方案依赖 LLM 遵守约定，不是硬保证**——这正是 EvoFlow 模式②的弱点。

**⇒ 因此在 §4.3 给出一个不依赖 LLM 的兜底。**

### 4.3 兜底：`cite` 的代理指标

| 方案 | 可靠性 | 成本 |
| --- | --- | --- |
| **A. LLM 显式回执**（§4.2） | 🟡 依赖 LLM 遵守 | 低 |
| **B. 检索命中后是否进最终输出**（语义相似度比对） | 🟡 需额外模型调用 | 中 |
| **C. 只看 `use_count`**（检索命中） | 🟢 客观、零依赖 | **但有噪声** |
| **D. 人工标注**（所有者标记"这条有用"） | 🟢 最准 | **人力贵** |

**建议：A + C 并存**——`use_count` 作**客观基线**（一定有数），`cite_count` 作**精确信号**（有更好）。
**⇒ 且明确：`hot`/`cold` 榜的排序用 `use_count`**（客观），`cite_count` 作**辅助列**。

### 4.4 输出面

| 面 | 内容 |
| --- | --- |
| **API** | `GET /api/v1/memory/stats` —— 返回四类载体的计数 + hot 榜（Top N）+ cold 榜（stale）。**分页口径见下。** |
| **UI** | 「沉淀层健康」看板（**放哪见 §10.1 V1**） |
| **判据②看板** | 四指标的一段连续时间序列（**这是判据②的验收界面**） |

**分页口径（2026-09-24 补 —— `decision-log.md` **D-058①** 评审附条件）**

| 面 | 口径 |
| --- | --- |
| 计数部分（四类载体总数） | **不翻页** —— 是标量聚合，不是列表 |
| **hot 榜 / cold 榜 / stale 列表** | **必须分页**：`limit`（1–200，**默认 20**）+ `offset`（≥ 0，**默认 0**）；响应含 `total`（**命中总数**，不是本页条数）+ `limit` + `offset` |
| 非法值 | `limit` 越界 / 非整数、`offset` 为负 ⇒ **`422`** |
| **不静默截断** | `items` 恒为分页后的**一页**；客户端据 `total` 与 `items.length` 判断是否还有下一页 |
| **排序确定性** | hot 用 `use_count` 降序、cold 用升序；**同值时以实体 id 升序作稳定次序** —— 否则翻页会**漏项或重复** |

> **⚠️ 为什么必须补**（附条件原文）：§4.4 有**列表端点**却未定义分页，与既有契约「**列表必须分页**」（[`docs/api-contract.md`](file:///d:/徐徐AI学习/公司工作台/docs/api-contract.md)）**相悖**。沉淀物数量随时间**单调增长**，无分页的 Top N 在多租户下会退化为「只看得到前几条」。
> **✅ 本条已补入正文 ⇒ D-058① 的附条件已履行，本规格可视为定稿**（口径仍以评审结论为准）。

## 5. 设计：控制器（补⑥——**本文的核心价值**）

### 5.1 三档动作

```
某条沉淀物在观察窗口内 use_count = 0
        ↓
① 标记      进 cold 榜（只读展示，零副作用）
        ↓ （持续 N 天仍为 0）
② 告警      进"沉淀层健康"看板的待处置清单 + 通知所有者
        ↓ （人工决定）
③ 处置      归档 / 重写 / 软删 —— **人工执行**
```

### 5.2 ⚠️ 自动化边界（**这条必须写死**）

**参照 P6 已评审的红线**：

> **自动只允许回滚/停用；自动晋升禁止**
> 候选**无生效路径**；走全量校验链；生成者 ≠ 评审者

**⇒ 本文的控制器**：

| 动作 | 可否自动 |
| --- | --- |
| 标记（进 cold 榜） | ✅ 自动 |
| 告警（进待处置清单） | ✅ 自动 |
| **归档 / 重写 / 删** | ❌ **必须人工** |
| **晋升为技能** | ❌ **必须人工**（走 P4 准入闸门） |

**理由**：**"自动淘汰"会删掉人还没来得及看的沉淀物**——而沉淀层的价值恰恰是"用一年后比用一天前强"，一年内的东西不该被自动清掉。

### 5.3 与 P6b 的关系（**避免重复建设**）

| | P6b（未开工） | B5 控制器 |
| --- | --- | --- |
| 对象 | **技能包**的准入与灰度回滚 | **记忆/技能**的复用度量与处置 |
| 闸门 | 准入闸门 + 灰度 + 回滚 | **复用度量 + 冷榜 + 告警** |
| 关系 | **B5 的输出（复用度量）可作为 P6b 准入的前置信号** | — |

**⇒ 建议：B5 先行**（它更轻、更基础），P6b 在 B5 的度量之上再做准入。

## 6. 设计：craft → skill 硬晋升（抄④）

### 6.1 为什么这条最重要

**EvoFlow 全项目唯一把"经验"变成"运行时强制能力"的机制**。原话：

> 记忆停留在"注入提示词"层面**永远会被 LLM 忽略**；**只有变成工具/技能，复用才是被强制的**。

### 6.2 设计

```
一条记忆累积到阈值（use_count 或 cite_count ≥ N）
        ↓
   生成**候选技能包**（不自动生效）
        ↓
   走 P4 既有准入闸门（来源白名单 + hash + 人工审核）
        ↓
   super_admin 审核通过 → 登记为技能 → 可绑定到数字员工
```

**⚠️ 关键约束（与 P6 一致）**：**候选无生效路径**——生成不等于启用，必须过 P4 的闸门。

**⚠️ 与 P4 口径的关系**：候选技能包的 `source_key` **走 P4 的部署注入白名单**——**不新增来源通道**（B4 的口径冲突在此不引入）。

## 7. 设计：记忆生命周期（衰减 / GC / 合并）

### 7.1 设计取向：**确定性、可重跑、无 LLM**

**借 EvoFlow 的做法**（其 `consolidate.py` 是**确定性算法、无 LLM 调用**，可全量重跑、可解释、可测试）：

| 阶段 | 逻辑 | 是否用 LLM |
| --- | --- | --- |
| **合并** | 同主体 / 高相似度的记忆合并 | ❌ 确定性 |
| **衰减** | `vitality` 按时间指数衰减 | ❌ 确定性 |
| **GC** | 低 `vitality` + 长期闲置 → **软删** | ❌ 确定性 |

**⚠️ 这与 P3 的约束兼容**：P3 明确「**不做 LLM 自动改写人格**」（§1.2-4）——本文的衰减/GC/合并**都是确定性操作，不涉及 LLM 改写**。

### 7.2 ⚠️ 但有两条 P3 的约束必须尊重

| P3 约束 | 本文的遵守 |
| --- | --- |
| 规则类记忆写入**强制人工在环**（生成者 ≠ 评审者） | **衰减不删规则类**——规则类的处置一律人工 |
| 不做 LLM 自动改写人格 | 合并**只做机械合并**（不重写语义） |

### 7.3 ⚠️ 第三条是本文自己的约束

**衰减不能影响"可检索性"**——否则会出现"某条记忆明明还在，却检索不到"。

**⇒ 建议**：衰减只影响**排序权重**（`score × vitality`），**不影响是否返回**；只有进入 GC 阶段才是真正的软删。

**⚠️ 阈值全部走配置**（外置，与 P3/P4 的 fail-closed 取向一致）。

## 9. 验收标准

| # | 验收项 | 证据形式 |
| --- | --- | --- |
| **A1** | **判据②的四个指标均可查询** | `GET /memory/stats` 返回四类计数 |
| **A2** | **能回答「这个月沉淀层在长吗」** | 连续两段窗口的对比数据 |
| **A3** | hot / cold 榜可查且排序正确 | 构造数据实测 |
| **A4** | 零复用沉淀物**能进 cold 榜并被告警** | 构造零引用数据 → 出现在待处置清单 |
| **A5** | **计量字段确实被写入**（防 EvoFlow 那个断点） | **写入点必须有调用方**——用集成测试断言 `use_count` 在检索后真的变了 |
| **A6** | **自动动作只有标记与告警**，无删除/晋升 | 代码审计：删除与晋升路径均需人工触发 |
| **A7** | 衰减**不影响可检索性**（只影响排序） | 构造低 vitality 数据 → 仍可检索到 |
| **A8** | 合并/衰减/GC 是**确定性的、可重跑** | 同一输入跑两次结果一致 |
| **A9** | **反假测试** —— 故意让 `cite_count` 不递增 ⇒ A5 必须变红 | 反假记录 |
| **A10** | **hot / cold / stale 三处列表均分页**（`limit` + `offset` + `total`；非法值 `422`；**同值排序稳定**） | 构造 **超过一页**的数据实测翻页 —— **不漏项、不重复** |

**⚠️ A5 是针对 EvoFlow 那个真实断点专门设的验收项**（`bump_craft_hit()` 无调用者 ⇒ `hit_count` 恒为 0）。**本文不允许重复这个错误。**
