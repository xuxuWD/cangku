## 1. 最重要的五个发现

### 1.1  许可证现实：功能最全的开源 CRM **几乎全是 AGPL/GPL**，只有「自建」能走通

| 阵营 | 项目（许可证，一手核实） | 对本项目 |
| --- | --- | --- |
| **AGPL-3.0（严禁引入代码）** | SuiteCRM、**EspoCRM**（LICENSE.txt 实为 AGPL，非 GPL）、Twenty（主体 AGPL，仅 `twenty-sdk/ui/shared` 等子包 MIT）、**Frappe CRM / Frappe Helpdesk**、Zammad、FreeScout、CiviCRM、Monica、listmonk、Keila | 多租户 SaaS 的网络服务条款雷区：**链入即触发传染**，只可「独立进程 + 已发布 API」隔离使用 |
| **GPL-3.0（不可并入服务端代码）** | ERPNext、Dolibarr、Tryton、**Mautic**（无网络条款 ⇒ 自用/独立部署安全） | 仅可**独立部署的可选集成件** |
| **许可证干净（可引用/借鉴）** | **Krayin CRM（MIT）**、**Odoo Community（LGPLv3）**、**Chatwoot（MIT 核心，`enterprise/` 专有）**、**Activepieces（MIT 核心）**、osTicket（GPL-2.0）、**PyMC-Marketing（Apache-2.0）** | Krayin = 最佳参照与（MIT）可引用来源；Odoo = 业务流参照 |
| **「伪开源」中国系（排除）** | **悟空 CRM**（新版《非商业使用协议》；老版协议明文「企业内部使用视为商用须购买授权、禁止基于其开发 SaaS」）、**CordysCRM**（GPLv3 + 不得修改 Logo 附加限制） | **排除**，不得凭「开源」印象取用 |
| **商用受限（排除嵌入）** | **n8n**（Sustainable Use License：官方明确**禁止作为多租户 SaaS 后端集成引擎**，违规自动终止）、**Windmill CE**（二进制含专有代码，禁 wrap/托管/转售） | 仅可作内部运维工具 |
| **付费墙** | Odoo 营销自动化/Helpdesk/Studio、EspoCRM Sales Pack/Advanced Pack、Vtiger Calculus AI、SuiteCRM AI 插件 | 排除（不采购即为不存在） |

**判据（可复用）**：GPL/AGPL 项目仅当「**独立进程 + 只经已发布 API/网络通信 + 边界隔离 + 不复制代码**」时可用（CiviCRM 官方 License FAQ 认可此界分）。

### 1.2 结论：企业级 CRM 的**功能本体必须自建**，开源项目价值 = 参照设计 + 少数独立集成件

四路调研一致：**没有任何项目**同时满足「许可证干净 + 原生多租户 + 可只嵌一个模块 + 客户主数据可外置」。所有工单/门户项目**强制自己的 Customer/Contact 表为主表**——而我们要求客户主数据与 RBAC / 审批 / 审计同源（多租户唯一事实源不可分裂）。⇒ **主数据 + 报价-合同-发票台账 + 工单 + 智能化 = 自建**；营销自动化与实时会话可作**可选独立集成件**（§6.3）。

### 1.3 智能化：**开源 CRM 的 AI 能力全部在付费墙内** ⇒ 智能化层也自建（这正是差异化）

| 项目 | AI 现状（一手） |
| --- | --- |
| Odoo 19 | 预测性线索评分（朴素贝叶斯）、Ask AI、OCR —— **仅 Enterprise** |
| EspoCRM | Intelligence 扩展（付费；条款**禁止托管转售与训练用途**） |
| SuiteCRM | 无本体 AI；商店插件付费（SuiteAI 约 $990/年） |
| Vtiger | Calculus AI 付费（约 $12/用户/月 + token 另计） |
| Frappe 生态 | 第三方 aiEmployeesFrappe（Apache-2.0，190+ 工具）——生态件，非本体 |
| Twenty | 原生 MCP server / AI Agents；自托管免费版可用性**待核实** |

⇒ 我们的智能化（健康度 / 跟进计划 / 多维度进度 / 对话式管理）**没有现成开源组件可拿来即用**，但**方法先例充分**（§4）——用「规则 + LLM + 证据引用」自建，恰是立项文档 §2.2 C 已定的差异点（「这部分必然自建」）。

### 1.4 中国落地：**发票与电子签署都存在"自建做不了"的法定环节** ⇒ 必须做 provider 抽象层

- **发票**：数电发票全国推广（税务总局公告 2024 年第 11 号，税局平台**免费**开票）；但**企业直连（乐企）门槛极高**（纳税信用 A/B、营收与开票量门槛、须报备自有系统并接受在线审计）；普通企业现实路径 = **服务商 API**（百望/航信/税航等，实施费 + 年费 + 按次，样本：9000–18000 元实施 + 3000–3500 元/年；阿里云市场上架按次计费）。**自建只能到**「开票申请单 + 台账 + 红冲编排 + 版式文件 + OFD/XML 解析」；**法定"开具"环节必须外部通道**。市面「Python 发票 SDK」多为 RPA 模拟登录电子税局（合规与稳定性存疑）。
- **电子合同**：第三方（e签宝 / 法大大 / 契约锁）按份或私有化（契约锁样本约 ¥28 万一次性 + 年服务费）；《电子签名法》第 13/14/16 条要求可靠电子签名（专有控制 + 可发现改动 + 必要时第三方认证）。**自建可做到防篡改，难以独立满足"身份可信 + 举证"** ⇒ 第一版 = 模板 + 审批 + 附件 + 状态台账 + **对接持牌签署方（provider 抽象）**。开源候选：**开放签企业版**（2025-09 全栈开源、国密 SM2、支持私有化多租户，**许可证细节待核实**）、`iText-GM`（Apache-2.0，国密 PDF 签章，需自备证书与验签服务）、DocuSeal（非国密，无国内 CA 资质）。

### 1.5 PIPL：**"电话类私密信息不可读取"可以落地为字段级密级**，且是法定方向的加强版

用户要求（工作台/AI 可读全量信息，**电话类私密信息除外**）与 PIPL 的「最小必要 + 字段级权限 + 脱敏展示」完全同向：
- 联系人电话/邮箱等**敏感字段**：列表默认掩码、明文查看需单独授权并留痕、**不进 AI 输入、不经数字员工工具返回**；
- 其余业务字段（客户名/行业/商机/活动/金额/阶段/工单/合同状态/发票状态）：**全部可被智能层读取**（§4 的智能分析建立其上）；
- 另需：操作留痕（谁看了/导出了哪些字段）、离职/转岗权限回收、**导出与删除接口**（PIPL 第 47 条）、跨境默认禁止。

## 3. 值得抄的设计清单（借设计，不搬码）

1. **报价-合同-发票联动**（Odoo/Dolibarr）：报价确认 → 生成合同/订单 → 生成发票 → 收款核销，**单向状态推进**；**已确认单据禁止回改**，只能作废重开。
2. **状态机**（Tryton）：`Draft → Quotation → Running → Closed / Cancelled` + 异常挂起（sale exception）；ERPNext 的 submit/cancel/amend **不可变单据**模型。
3. **权限模型**（EspoCRM ACL：`all/team/own/no` + 团队层级；Odoo record rules：domain 表达式行级过滤 + 组继承）⇒ 直接映射到我们的 RBAC；**再加字段级密级（§1.5）**。
4. **元数据驱动建模**（Twenty object/metadata、Krayin 自定义属性挂载任意实体）⇒ 自定义字段 = 元数据表 + JSONB（我们 P5 草案已采纳，保留）。
5. **工单门户 IA**（Frappe Helpdesk / Libredesk）：Team/SLA/Agent 三段 + 客户自助门户（知识库前置 + 工单绑客户实体）；Chatwoot 的「会话 → 工单」转化。
6. **多租户**（Trytond 一服务多库 / Frappe 一 site 一库）⇒ 均优于 Odoo 单库多公司；我们沿用自有复合外键方案（已强于全部参照）。

## 4. 智能化设计输入（方法先例 + 指标字典 + 防幻觉）

### 4.1 方法先例（自建可实现，第一期不训模型）

| 能力 | 先例与方法 | 我们的第一期做法 |
| --- | --- | --- |
| 线索/商机赢率评分 | Odoo 预测性线索评分：朴素贝叶斯 `P(Won\|A∩B) ∝ P(A\|Won)·P(B\|Won)·P(Won)`；**样本 ≥20 条胜负记录才启用** | **规则分先行**（阶段 + 金额 + 互动 + 来源质量）；样本达标后再上朴素贝叶斯（可解释、无需训练设施） |
| 客户健康度 / 流失预警 | 行业通行：**可解释五维加权规则**（产品使用 30–45% / 参与 15–20% / 财务 10–15% / 情感 15–20% / 关系 10–15%），分档 Green≥80 / Yellow 60–79 / Red<60 | 五维规则分（我们的维度映射见 §4.3）；XGBoost+SHAP 等**列为后续专项** |
| 续约/复购留存 | **PyMC-Marketing（Apache-2.0，可商用）**：BG/NBD、Pareto/NBD、Shifted Beta Geometric | 第一版用规则（合同到期窗口 + 历史续约）；**库本身可选引入**（许可证干净） |
| 下一步最佳动作（NBA） | Salesforce 公开方案：**signal（评分）+ business logic（阈值/优先级）+ knowledge（组织经验）→ 推荐（动作+对象+理由+预期影响）**；LinkedIn Account Prioritizer（arXiv:2306.07464）用 ML 排序 + 实例级解释（A/B 实测 +8.08% 续约预订额，采纳率 85%） | **跟进计划生成器**：候选动作集（打电话/发资料/约演示/报价/续约提醒/升级/搁置）+ 评分排序 + **每条建议附"理由 + 依据证据引用"**（§4.4） |
| CRM Copilot / MCP | Twenty 原生 MCP（OAuth 读写）；HubSpot Remote MCP 已 GA；Salesforce Headless 360 MCP（Beta，仅 4 工具以省 context）；社区 MCP（`salesforcecli/mcp` Apache-2.0 等） | 我们的数字员工 + 受控工具面**已是同构能力**；**权限继承原则**：agent 只能执行登录用户本人被许可的动作且留审计；⚠️ 2026 年 1–2 月 MCP 生态 60 天 30 个 CVE（含 RCE）⇒ 工具面白名单与参数校验不可放松 |

### 4.2 多维度进度：指标字典（草案，供 P5 规格引用）

| 指标 | 定义 | 所需字段 |
| --- | --- | --- |
| 管线覆盖率 | 合格管线总额 ÷ 同期目标；健康 3–5x | 商机金额、阶段、预计成交日、目标（配额） |
| 赢率 | 赢单数 ÷ 总商机数（按金额分档校准） | 商机状态、关闭日、金额 |
| 销售周期长度 | 创建 → 成交天数（按金额分档） | created_at、closed_at |
| 阶段转化率 | 进入下一阶段数 ÷ 进入本阶段数 | 阶段变更事件 + 时间戳 |
| 管线账龄 | 商机在当前阶段停留天数 | `stage_entered_at` |
| 管线创建速率 | 周期内新建合格商机数 | 创建时间 + 合格标记 |
| 健康度分档 | 五维加权分 → A/B/C/D（或 G/Y/R） | §4.1 维度所需字段 |
| 流失/沉默风险分层 | 风险分档 + 路由（人工 / 自动化 playbook） | 健康分、最后互动日、工单情况 |
| SLA 达成 | 按时首次响应/解决 ÷ 总工单 | 工单创建、首响、解决时间、严重度 |
| 续约窗口 | 到期前 N 天（建议 90）提升评分频率 | 合同到期日、续约状态 |
| 发票/回款进度 | 已开票金额 ÷ 合同金额；逾期未回款笔数 | 合同金额、发票台账、回款状态 |
| 目标达成度 | 各责任人/团队 目标 vs 实际（金额/单数/活动量） | 目标设置、商机、活动 |

### 4.3 我们 CRM 的健康度五维映射（建议）

| 维 | 我们可取的信号 | 权重（缺省） |
| --- | --- | --- |
| 互动活跃度 | 近 N 天活动数、最后互动距今天数 | 30% |

### 4.4 防幻觉与可信度（5 条硬做法，写入规格）

1. **检索接地 + 具名拒答**：建议必须能定位到本租户内的证据（活动/商机/工单/合同记录引用）；**数据不足时明确输出「依据不足，无法给出建议」**，禁止补全（OWASP LLM09:2025）。
2. **引用校验**：生成后逐条核对关键主张是否被所引记录支持，识别「引用伪装」；校验不通过的条目**丢弃并在 UI 标注**。
3. **Schema 约束输出 + 置信度暴露**：JSON Schema 固定字段（动作类型 / 对象 ID / 理由 / 证据引用 / 置信度），UI 显示不确定度。
4. **分层 HITL 审批闸门**（复用既有九步闸门与审批）：只读 / 低风险写 / 高风险写（改金额、发通知、改关键字段）分层；**LLM 建议永不直接执行**。
5. **脱敏审计**：留存「问题 + 证据引用 ID + 校验结果」，**不落敏感字段**；自洽性采样不一致者转人工队列。

## 5. 中国落地约束（对我们的硬约束）

### 5.1 发票

- 自建：**开票申请单 + 发票台账 + 红冲流程编排 + 版式文件生成 + OFD/XML 解析**（OFD 本质 ZIP+XML，解析可用 `easyofd` 等，**许可证待核实**；数电票版式**生成**无成熟开源，需按国标自研 210×140mm 等版式）。
- 外部：**法定"开具"必须经电子发票服务平台或持牌服务商/乐企通道**；服务商对接需资质与商务（§6.3 外部依赖）。
- 三条硬约束：① 发票模块按「申请单 + 台账 + provider 抽象层」设计，**不承诺自研开票**；② provider 对接**幂等（业务流水号）+ 超时重试上限 + 失败降级人工**，禁止同步阻塞在请求链路；③ 金额整数分/Decimal；XML/版式文件**走对象存储，不入库**。

### 5.2 电子合同 / 签署

- 第一版 = **模板 + 内部审批 + 附件归档 + 状态台账 + 签署记录留存 + provider 抽象**；**不承诺**自建法律效力级签署、不承诺自建 CA。
- 合同表 **provider 无关**：签章渠道、签署任务 ID、存证哈希、证据报告字段预留。
- 状态取值显式枚举（草稿/审批中/待签/已签/已作废/已过期）；多表变更包事务；全流程留痕。
- 开源候选评估（**许可证与法律效力细节待核实**）：开放签企业版（国密 SM2 / GB/T 38540-2020 / 支持私有化多租户 / 2025-09 全栈开源）、`iText-GM`（Apache-2.0，需自备证书与验签设施）、DocuSeal（非国密、无国内 CA 资质，不适合作为效力来源）。

### 5.3 个人信息（PIPL）

- 字段级密级：**敏感字段（电话、邮箱、证件、银行账号等）列表默认掩码、明文查看单独授权并留痕、不进 AI 输入、不经工具返回**；其余字段智能层可读（满足用户要求）。
- 操作留痕（谁、何时、看了/导出了哪些字段）；**离职/转岗自动回收数据权限**；导出走白名单 + 审批 + 水印。
- **导出与删除接口**（PIPL 第 47 条）必须可执行，删除覆盖主表 + 附件 + 日志副本；**跨境默认禁止**（含境外 SaaS/云）。
- 处理敏感信息/自动化决策等场景需**个人信息保护影响评估**（第 55 条）——登记为合规动作项。

### 5.4 触达渠道（短信 / 邮件）

- **短信只能对接云厂商 API**（腾讯云/阿里云均要求企业实名 + 签名/模板报备 + 资质）；营销短信须先取得同意、拒绝后停止发送；自建通道（自有码号 + 电信许可）不现实。
- **营销邮件**须：标题前部注明「广告」或「AD」、提供 30 日内有效的退订方式、SPF/DKIM/DMARC；**事务性与营销性发信域/IP 分离**；阿里云企业邮箱等**禁止发营销邮件**，营销须用专用 ESP（可自建 listmonk + 独立子域，或用 Mautic 托管旅程）。
- **同意/订阅记录是硬要求**：所有触达必须有独立同意记录（时间、渠道、来源、证据），**一键退订全局生效**。

## 6. 改造提案（供评审）

### 6.1 总路线

**自建企业级 CRM 本体（客户主数据 + 报价/合同/发票台账 + 工单门户 + 智能化），以开源项目为「设计参照」；营销自动化与实时会话按需选「独立集成件」。** 理由：① 主数据必须与 RBAC/审批/审计同源（多租户唯一事实源不可分裂）；② 许可证现实（§1.1）；③ 智能化无现成组件（§1.3），而它正是本平台既有数字员工/知识/记忆能力的落点。

### 6.2 分期建议（P5 拆为三段，各自独立可验收）

| 段 | 内容 | 依赖 |
| --- | --- | --- |
| **P5a 客户主数据 + 商务主线 + 智能化打底** | 客户/联系人/线索/商机/活动（含**字段级密级**）+ **报价 → 合同 → 发票台账**（provider 抽象，先只做台账与版式文件）+ 商机阶段机 + **健康度五维规则分** + **多维度进度指标** + **跟进计划生成器（NBA，规则 + LLM 解读，带证据引用）** + 受控工具面（数字员工读写 CRM） | 无外部依赖（发票/签署先只做"申请单 + 台账"侧） |
| **P5b 工单门户 + SLA** | 工单（客户提交 / 分派 / SLA / 升级）+ 自助门户（**我们签发 OIDC，门户当 SP**）+ 知识库前置 + 「会话→工单」；参照 Libredesk/Frappe Helpdesk/osTicket 的 IA | 无外部依赖 |
| **P5c 营销自动化 + 触达合规** | 分群 / 旅程 / 落地页 / 评分 + **同意与订阅中心（硬前置）** + 邮件发送（自建发送器 或 Mautic 集成件）+ 短信走云厂商 API（模板/签名报备） | 邮件：Mautic 集成件决策 + ESP 域配置；短信：云厂商账号与报备（**外部依赖**） |

> **⚠️ 最终裁决修订（2026-09-17，用户评审，覆盖上表）**：「**发票和电子签章暂时不需要，留个口就行**，等交付后二期做迭代优化再开发；**工单和客服门户**也是一样**留口等二期**；**触达渠道（短信 / 邮件）**也二期开发；**所有的合同进度和回款之类的都可以先做人工上传、输入**。」⇒ 实际分期为：**一期 = P5a**（客户主数据 + 报价 → 合同[人工上传 / 人工输入] + 智能化打底；**不含发票、不含签署 provider**）；**二期 = 发票模块（含 provider） / 电子签章 provider / 工单门户 + SLA / 营销自动化 + 触达渠道**（占位与扩展点见 P5a 规格 §1.5）。本报告 §5.1/§5.2 的发票与签署约束**仍然有效**（作为二期设计输入）。

### 6.3 外部依赖清单（非代码可解决，需商务决策）

| # | 依赖 | 用途 | 影响 |
| --- | --- | --- | --- |
| 1 | **数电发票服务商**（百望/航信/税航等） | 真正开票（法定效力环节） | P5a 的「开票」动作；未接通前只做申请单 + 台账（**登记为未验证**） |
